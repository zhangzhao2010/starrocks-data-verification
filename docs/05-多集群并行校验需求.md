## 1. 背景

现网存在三组固定对应的华为云与阿里云 StarRocks 集群。v1.3 只支持一组固定的 `huawei ↔ aliyun` 校验，不能在同一套系统内管理三组集群。

当前调度严格按 COUNT、METRIC、SAMPLE 顺序领取任务。约 20 万个 COUNT 在一晚只完成 5 万余个，METRIC 和 SAMPLE 因 COUNT 长期积压而未开始。现网缺少按集群、检查类型统计的耗时、吞吐和超时指标，无法据此确定安全并发。

## 2. 目标

| 编号 | 目标 |
|---|---|
| G1 | 一套系统同时管理六个物理集群和三个固定校验组 |
| G2 | 三个校验组同时运行，且任务、凭证和结果严格隔离 |
| G3 | COUNT、METRIC、SAMPLE 使用独立并发池并同时推进 |
| G4 | 计划支持选择一个、多个或全部校验组 |
| G5 | 提供“集群 × 检查类型”吞吐、耗时、积压和超时指标 |
| G6 | 通过压测调整并发，目标在 20:00–07:30 完成一轮 |

## 3. 已确认业务规则

### 3.1 集群与校验组

- 共六个物理集群：华为侧三个、阿里侧三个。
- 组成三个固定校验组：`H1 ↔ A1`、`H2 ↔ A2`、`H3 ↔ A3`。
- 每个校验组恰有一个 SOURCE 集群和一个 TARGET 集群。
- 不支持 `H1 ↔ A2` 等跨组组合，也不支持三方比较。
- 每个物理集群只能属于一个启用的校验组。
- 集群和校验组使用用户配置的稳定 ID，名称仅用于展示。

### 3.2 资产归属与映射

- 一个逻辑资产只属于一个校验组。
- 同一资产在组内两端分别配置数据库名和表名。
- 同一物理表不能在同一校验组内重复绑定到多个资产。
- 资产导入必须指定校验组；预览阶段拒绝未知或停用的校验组。

### 3.3 计划与运行

- 计划可选择一个、多个或全部校验组。
- 单次运行只冻结所选校验组中的资产、范围和规则。
- 运行结果提供总体视图，并支持按校验组查看。
- 单组失败不应阻止其他组继续执行。
- 复查、暂停、取消、报告和审计必须保留校验组上下文。

## 4. 并发与调度需求

### 4.1 独立并发池

每个物理集群必须显式配置以下五个并发值：

- COUNT
- METRIC
- SAMPLE
- METADATA
- DEEP

COUNT、METRIC、SAMPLE 是三个完全独立的业务池；METADATA 和 DEEP 是独立的小型管理/诊断池。

- 各池不得占用其他池的并发额度。
- 不设置物理集群总并发上限。
- 空闲额度不在池之间借用。
- 六个集群的并发值分别配置，不使用隐含默认值。
- 并发配置由使用者根据监控和压测结果调整。

### 4.2 公平性

- COUNT 大量积压时，METRIC 和 SAMPLE 仍能立即领取任务。
- 每类任务独立物化、独立领取，不按全局类型优先级截断候选集。
- 候选集中前若干任务因资产锁、预算、窗口或授权不可执行时，调度器必须继续寻找后续可执行任务。
- 同一观察的 SOURCE/TARGET 两端结果仍必须配对后才能比较。
- 同一资产跨运行串行约束继续保留。

### 4.3 负载保护

本迭代不自动降低并发，也不因监测信号自动停止集群：

- 系统采集并展示超时、慢查询和 StarRocks 负载信号。
- 达到阈值时产生告警事件。
- 调整并发和恢复执行由使用者手工完成。
- 查询超时、执行窗口、取消确认和租约安全机制继续生效。

## 5. 规模和性能目标

估算单轮规模：

| 类型 | 逻辑校验数 |
|---|---:|
| COUNT | 约 200,000 |
| METRIC | 约 100,000 |
| SAMPLE | 约 50,000 |
| 合计 | 约 350,000 |

每个逻辑校验通常产生两条端侧查询，因此约为 700,000 条查询。11.5 小时派发窗口内完成，需要六个集群合计持续约 16.9 条查询/秒；按 20% 余量，容量验收目标为至少 20.3 条查询/秒。

该数值只用于容量规划。最终并发必须根据真实平均耗时、P95、超时率和生产负载压测确定，不能直接由当前并发 40 推导。

## 6. 可观测性需求

Dashboard 至少按“物理集群 × 检查类型”展示：

- 配置并发、当前在途、并发利用率；
- READY 数量和最老等待时间；
- 最近一小时完成量和完成速率；
- 平均、P50、P95、最大执行时长；
- 成功、失败、取消和超时数量及比率；
- 剩余任务预计完成时间；
- Worker 心跳、注册代次、待发箱和本地材料配额状态；
- StarRocks running/pending query 等已配置负载信号。

指标不足时不得宣称已达到夜间完成目标。

## 7. 配置、凭证和部署

- 每个物理集群使用独立只读凭证、Worker token、系统用户、数据目录和 Executor 实例。
- Controller 和 Web 不读取 StarRocks 凭证。
- Worker token 绑定单一物理集群，禁止领取其他集群任务。
- 集中部署模式下运行一个 Controller、一个 Web、六个 Executor。
- 配置检查必须拒绝重复集群 ID、重复集群归属、无效校验组、缺失并发值和缺失凭证引用。

## 8. 数据迁移和兼容

- 使用增量数据库迁移保留历史资产、运行、结果、差异和审计数据。
- 旧版单校验组数据迁移到明确指定的 legacy 校验组。
- 旧配置不能被静默解释为任意三组配置；升级前必须完成配置检查。
- 新资产导入格式增加 `pair_id`。
- 协议升级后，旧 Worker 不得继续领取新协议任务。

## 9. 非目标

本迭代不实现：

- 任意两个物理集群临时组对；
- 三方或 N 方一致性比较；
- 集群间共享或动态借用并发额度；
- 自动调优并发；
- 基于 CPU/内存的 Executor 自动扩缩容；
- 多租户、账号和权限系统。

## 10. 验收标准

1. 六个 Executor 可同时注册，且只能领取各自物理集群任务。
2. 三个校验组无跨组任务、结果或比较。
3. 计划可选择单组、多组和全部，运行资产集合准确。
4. COUNT 持续积压时，METRIC、SAMPLE 仍按各自并发持续执行。
5. 每个“集群 × 类型”的在途数不超过其配置值，且不存在额外总上限。
6. 前 200 个候选不可执行时，后续可执行任务仍能被领取。
7. Dashboard 能提供压测所需的积压、吞吐、耗时和超时指标。
8. 数据库升级保留旧数据，并将其归入指定 legacy 校验组。
9. 三组同时运行时，约 35 万逻辑校验可经实测在 07:30 前完成，并保留至少 20% 吞吐余量。
