## 1. 系统概览

### 1.1 它做什么

srdq 是一个**只读**的数据一致性校验程序。它在每天固定的执行窗口内，对比三个固定校验组中的华为云 StarRocks（SOURCE）和阿里云 StarRocks（TARGET），并输出差异和日报。一个逻辑资产只属于一个校验组，SOURCE/TARGET 可以使用不同库表名，系统不进行跨组比较。

校验分四档，从粗到细：

| 档位 | 内容 | 规则来源 | 是否需要批准 |
|---|---|---|---|
| COUNT | 按分区比对行数 | 导入资产时自动生成 `baseline_count` 规则 | 自动批准 |
| METRIC | 分组聚合比对：行数、非空数、金额合计 | 导入 `metric_rules_*.csv` | 需要批准 |
| SAMPLE | 按主键哈希分桶抽样，逐行比对指定列 | 导入 `sample_rules_*.csv` | 需要批准 |
| DEEP | 深度逐行比对 | 只能由“手工复核”发起 | 随复核请求确认 |

每个物理集群分别配置 COUNT、METRIC、SAMPLE、METADATA、DEEP 五个独立并发池。各池同时领取工作、不互相借用并发；同一池内先按优先级（核心表 90，其他表 50），再按层级（ODS → DWD → DWS → ADS → DIM → OTHER）。

程序**只读两端 StarRocks**，不会写入或修改业务数据。

### 1.2 部署架构

所有组件都部署在阿里云的**一台 ECS** 上：

```text
运维/使用人员浏览器 ──HTTP──► ECS <IP>:8470  srdq-web（看板 + REST /v1，监听 0.0.0.0）
                                              │
                                              ▼
                                         srdq-controller（调度、窗口、报告；API 127.0.0.1:8471）
                                              │ Unix socket /run/srdq-pg
                                              ▼
                                         srdq-pg（内置 PostgreSQL 16，控制库，不监听 TCP）
                                              ▲
        ┌─────────────────────────────────────┼─────────────────────────────────────┐
   pair-1：huawei-1 ↔ aliyun-1           pair-2：huawei-2 ↔ aliyun-2           pair-3：huawei-3 ↔ aliyun-3
   每个物理集群一个独立 executor、系统用户、只读凭证、worker token 和数据目录
```

| systemd 单元 | 运行用户 | 作用 |
|---|---|---|
| `srdq-pg.service` | `srdq-pg` | 内置 PostgreSQL 16.2，只开放 Unix socket，`PrivateNetwork` 隔离 |
| `srdq-controller.service` | `srdq-ctl` | 调度、窗口控制、比对判定、报告生成。启动前自动执行 `srdq migrate` |
| `srdq-web.service` | `srdq-ctl` | Web 看板和 REST API，监听 0.0.0.0:8470 |
| `srdq-executor@<cluster-id>.service` | 每集群独立用户 | 六个物理集群各运行一个执行器，只持有本集群 SR 凭证 |
| `srdq-pg-backup.timer` | root | 每天 02:30（随机延迟最多 15 分钟）备份控制库，保留 14 天 |

安全约束如下：

- 凭证隔离：
  - controller 和 web 如果能读取任何 SR 凭证，就拒绝启动。
  - 每个执行器如果能读取其他物理集群的凭证，也拒绝启动。
- Web 没有登录，也不做来源或 IP 限制：能访问到 ECS 8470 端口的人都能操作。访问范围由阿里云安全组控制。

### 1.3 执行窗口（非常重要）

窗口时刻来自配置文件，时区为 Asia/Shanghai：

| 时刻 | 状态 | 行为 |
|---|---|---|
| 20:00 | OPEN（开窗） | 执行器开始领取工作，包括**范围发现**和检查 |
| 07:30 | DRAINING（收尾） | 不再开始新的观察，已开始的可以收尾 |
| 08:00 | CLOSED（关窗） | 取消在途查询并确认终止 |
| 08:15 | — | 自动生成当天日报（关窗后 15 分钟宽限） |

窗口关闭期间（08:00 到当天 20:00），**执行器不领取任何工作**，“范围发现”也不例外。因此：

- 白天点“开始发现”或“立即运行”后，要等到当天晚上 20:00 才会真正执行。这是正常行为。
- 一轮运行可以跨多个窗口，窗口用量会记在运行的 `windows_used` 里，没跑完的部分下个窗口继续。
- 只有在窗口开着时（20:00–次日 08:00），才能“延长窗口”或“提前关闭窗口”。

### 1.4 一套部署支持三个固定校验组

一个离线包、一台 ECS 同时配置六个物理集群和三个固定校验组：`pair-1`、`pair-2`、`pair-3`。每组由一个 SOURCE 集群和一个 TARGET 集群组成，系统只在组内比较。

交付的资产和规则文件可以按校验组分目录，例如数仓、监控、账单。每行 CSV 都必须填写配置中存在的 `pair_id`：

- 同名库表可以分别存在于不同校验组，不会互相冲突。
- 计划可以选择一个、多个或全部校验组。
- `pair_id` 写错会导致资产落入错误校验组，或在导入时因校验组不存在而报 ERROR；导入预览时必须核对。

## 2. 交付物说明

### 2.1 离线安装包

```text
srdq-offline-<版本>-alinux4-x86_64.tar.gz          # 安装包，权限 0600
srdq-offline-<版本>-alinux4-x86_64.tar.gz.sha256   # 校验文件
```

包内包含：

- 应用代码和所有依赖 wheel，安装时离线 pip 安装到独立 venv。
- PostgreSQL 16.2 二进制。
- systemd 单元、部署脚本（install、upgrade、rollback）和备份脚本。
- 生产配置 `provision/config.yaml`：
  - `run_enabled: true`，部署完成即可派发检查。
  - `transfer.global_approval_ref: "免审批"`，METRIC 和 SAMPLE 允许运行，批准规则时默认使用这个审批依据。
  - 窗口为 20:00 / 07:30 / 08:00（跨午夜）。
  - 六个 `physical_clusters`、三个 `cluster_pairs`，以及每个物理集群的 COUNT、METRIC、SAMPLE、METADATA、DEEP 并发。
- 六份物理集群凭证 `provision/secrets/<cluster-id>.json`，含**生产密码**。

> **安全要求**：安装包含生产密码，只能通过受控通道传输。不要放进 Git、网盘或普通制品库。安装完成后立即删除 ECS 上 `/tmp` 中的压缩包和解压目录。

### 2.2 资产与规则文件

每个集群一个目录，结构如下：

```text
<集群名>/
├── assets.csv                 # 资产清单：要校验哪些表
├── metric_rules_ods.csv       # METRIC 规则，按层级分文件
├── metric_rules_dwd.csv
├── metric_rules_dws.csv
├── metric_rules_ads.csv
├── metric_rules_dim.csv
├── metric_rules_other.csv
├── sample_rules_ods.csv       # SAMPLE 规则，按层级分文件
├── sample_rules_....csv
└── skipped.csv                # 未生成规则的表及原因（只读参考，不导入）
```

当前交付文件的规模如下（某层没有表时不生成对应文件，例如账单集群没有 ADS 和 OTHER）：

| 集群 | 资产（表） | METRIC 规则数 | SAMPLE 规则数 |
|---|---|---|---|
| 数仓集群 | 3475 | 约 3401 | 1250 |
| 监控集群 | 1008 | 约 990 | 601 |
| 账单集群 | 111 | 约 108 | 37 |

说明：

- METRIC 规则数按“表 + rule_key”计。CSV 每行是一个指标，同一张表、同一个 rule_key 的多行合起来是一条规则。
- 一张表最多有两条 METRIC 规则：
  - `nonnull_totals`：行数 + 各列非空数。
  - `amount_totals`：行数 + 金额列合计。
- 每张表最多一条 SAMPLE 规则，按单列主键抽样。
- 最大的文件是数仓集群的 `metric_rules_ods.csv`，约 2.1 MB，远低于 16 MiB 的导入上限。

**skipped.csv** 的列为 `layer,source_db,source_table,check,reason`，记录没有生成规则的表。常见原因：

| reason | 含义 | 影响 |
|---|---|---|
| `composite key (...)` | 主键是多列组合，SAMPLE 只支持单列键 | 该表没有 SAMPLE，COUNT 和 METRIC 照常 |
| `DUPLICATE model has no reliable unique key` | 明细模型表没有可靠唯一键 | 该表没有 SAMPLE |
| `no non-key column usable for SUM/COUNT_NONNULL; baseline COUNT covers it` | 没有可聚合的非键列 | 该表没有 METRIC，只做 COUNT |

这些表仍在资产清单里，每晚照样做 COUNT 校验。

### 2.3 文件格式（自行修改时参考）

所有文件都必须是 UTF-8 编码（带 BOM 也可以），逗号分隔，表头必须一字不差。

**assets.csv**

```csv
layer,pair_id,source_db,source_table,target_db,target_table,priority,enabled
ODS,pair-1,ods,ods_card_tb_user_card_info_ri,ods,ods_card_tb_user_card_info_ri,50,true
```

- `pair_id` 必须是配置中的校验组 ID。
- `layer` 取 ODS、DWD、DWS、ADS、DIM、OTHER 之一。
- `priority` 取 0–100，越大越先执行。
- `enabled` 取 true 或 false。

**metric_rules_*.csv**

```csv
pair_id,source_db,source_table,rule_key,group_by,filter,metric_id,function,column,scale,compare,rtol,atol
pair-1,dwd,dwd_account_trade_detail_1di_modify,amount_totals,,,row_cnt,COUNT_ROWS,,,EXACT,,
pair-1,dwd,dwd_account_trade_detail_1di_modify,amount_totals,,,sum_acct_trade_amount,SUM,acct_trade_amount,4,EXACT,,
```

- `pair_id` 和 SOURCE 库表共同定位资产。
- `function` 取 COUNT_ROWS、COUNT_NONNULL、SUM。
- `compare` 取 EXACT 或 TOLERANCE。TOLERANCE 时 `rtol` 和 `atol` 生效。
- `scale` 是 SUM 时的小数位。

**sample_rules_*.csv**

```csv
pair_id,source_db,source_table,key_column,compare_columns,float_rtol,float_atol
pair-1,dim,dim_test_merchant_list_info,merchant_no,merchant_no;merchant_type,,
```

- `pair_id` 和 SOURCE 库表共同定位资产。
- `compare_columns` 用分号分隔。
- `float_rtol` 和 `float_atol` 是浮点列的容差，可以留空。

## 3. 部署前准备

### 3.1 主机要求

| 项 | 要求 | 检查命令 |
|---|---|---|
| 操作系统 | Alibaba Cloud Linux 4，x86_64 | `cat /etc/os-release; uname -m` |
| glibc | ≥ 2.17 | `ldd --version \| head -1` |
| Python | 3.11，带 `venv` 模块 | `python3.11 -c 'import venv; print("ok")'` |
| 系统工具 | systemd、runuser、flock、tar、sha256sum | `command -v systemctl runuser flock tar sha256sum` |
| 权限 | root 或 sudo | `sudo -v` |
| 磁盘 | `/opt` 至少 2 GB；`/var/lib/srdq` 按控制库加 14 天备份预留，建议 ≥ 50 GB | `df -h /opt /var/lib` |
| 时间 | 已开启 NTP 同步。窗口按 Asia/Shanghai 计算，时间偏差会导致开关窗错位 | `timedatectl` |

如果缺少 Python 3.11，可以用系统源离线安装：`sudo dnf install -y python3.11`。这是唯一需要的系统包，生产机**不需要**外网、pip、uv，也不需要单独安装 PostgreSQL。

### 3.2 网络要求

| 方向 | 端口 | 说明 |
|---|---|---|
| ECS → 六个 StarRocks FE | 9030（以各 `<cluster-id>.json` 为准） | 对应物理集群的执行器查询 |
| 浏览器 → ECS | 8470 | 访问 Web 看板和 REST API |

在安全组中为使用人员所在网段放行 ECS 的 TCP 8470 入方向。8471 是执行器内部接口，只监听本机，不需要开放。ECS 必须能访问六个 FE。

连通性自检（对六个物理集群逐一执行）：

```bash
timeout 3 bash -c '</dev/tcp/<FE地址>/9030' && echo '<cluster-id> ok'
```

### 3.3 StarRocks 账号要求

六个物理集群都使用独立的**只读账号**，需要：

- 对待校验库表有 `SELECT` 权限。
- 能读取表结构和分区元数据（`information_schema`、`SHOW PARTITIONS` 等）。

权限不足的表会在范围清单中显示为 `ACCESS_DENIED`。

### 3.4 准备好的材料

- [ ] 离线包 `.tar.gz` 和 `.sha256` 两个文件。
- [ ] 确认离线包包含六个物理集群和三个校验组的正确配置与凭证。
- [ ] 三个校验组的资产和规则 CSV，且每行 `pair_id` 正确。
- [ ] 跳板机账号和 ECS 账号。

## 4. 首次安装

> 整个安装过程是一条命令。脚本会自动写入配置和凭证、创建隔离用户、初始化数据库、生成执行器令牌并启动所有服务，**无需手工编辑任何文件**。

### 4.1 上传并校验

在笔记本或构建机上：

```bash
scp -J <user>@<跳板机> srdq-offline-1.4.0-alinux4-x86_64.tar.gz* <user>@<ECS>:/tmp/
```

登录 ECS：

```bash
cd /tmp
VERSION=1.4.0
sha256sum -c "srdq-offline-${VERSION}-alinux4-x86_64.tar.gz.sha256"
# 期望输出：srdq-offline-1.4.0-alinux4-x86_64.tar.gz: OK
```

校验不通过就**不要继续**，重新传输。

### 4.2 解压并安装

```bash
tar xzf "srdq-offline-${VERSION}-alinux4-x86_64.tar.gz"
sudo "./srdq-offline-${VERSION}/deploy/install.sh"
```

安装脚本依次执行：

1. 校验包内 `SHA256SUMS`、主机架构、glibc、Python 3.11、systemd 等，然后加部署锁 `/run/srdq-deploy.lock`。
2. 创建系统组 `srdq`、`srdq-pg`，以及 `srdq-ctl`、`srdq-pg` 和六个执行器用户 `srdq-hw1`、`srdq-al1`、`srdq-hw2`、`srdq-al2`、`srdq-hw3`、`srdq-al3`。这些用户都是 nologin。
3. 把应用安装到 `/opt/srdq/releases/<版本>`（含独立 venv），PostgreSQL 安装到 `/opt/srdq/postgresql/<版本>`。
4. 安装 systemd 单元，并执行 `daemon-reload`。
5. 写入 `/etc/srdq/config.yaml` 和 `/etc/srdq/secrets/*.json`，设置好属主和权限。
6. 初始化 PostgreSQL，创建 `srdq-ctl` 角色和 `srdq` 库，并执行数据库迁移。
7. 为六个物理集群生成执行器令牌，写入各自的凭证文件。
8. 保存配置快照，把 `/opt/srdq/current` 原子指向新版本。
9. 执行 `systemctl enable --now`，启动 controller、web、六个 executor 和备份 timer。

成功时末尾会打印看板地址：

```text
Dashboard: http://<ecs-ip>:8470/
```

脚本中途失败时会打印错误原因并退出。修正后可以重新执行同一个命令。

> 同一版本号的另一个包（内容摘要不同）会被拒绝安装，提示 `bump project.version`。这种情况需要研发重新打一个递增版本号的包。

### 4.3 安装后检查

为方便操作，先定义一个别名（建议写进运维账号的 `~/.bashrc`）：

```bash
alias srdq='sudo -u srdq-ctl env SRDQ_CONFIG=/etc/srdq/config.yaml /opt/srdq/current/venv/bin/srdq'
```

> 本文后面出现的 `srdq <命令>` 都是指这个别名。

逐项检查：

```bash
# 1. 服务状态：PG、controller、web 和六个 executor 应为 active (running)，timer 为 active (waiting)
systemctl status srdq-pg srdq-controller srdq-web 'srdq-executor@*.service' --no-pager
systemctl list-timers srdq-pg-backup.timer --no-pager

# 2. 配置自检
srdq check-config
```

`check-config` 的期望结果：

- `run_enabled` 为 true，`transfer_approved` 为 true，`window` 为 `20:00-07:30-08:00 Asia/Shanghai`。
- 六个物理集群和三个校验组均通过校验。
- 六份 SR 凭证对 `srdq-ctl` 都不可读。这是正确的：controller 和 web 不能读取 SR 凭证。
- `credentials.controller_pg` 的 `readable_by_me` 为 true。

```bash
# 3. Web 健康检查
curl -s http://127.0.0.1:8470/v1/health
# 期望：{"status":"ok","schema_version":...,"now":"..."}

# 4. 看板摘要：control.status 为 ACTIVE（不是 RECOVERY），六个集群均有五类池统计
srdq status

# 5. 六个执行器是否注册成功
curl -s http://127.0.0.1:8470/v1/workers | python3.11 -m json.tool
```

执行器日志里不应该有反复的连接错误；对六个实例逐一检查：

```bash
journalctl -u srdq-executor@huawei-1 -n 50 --no-pager
journalctl -u srdq-executor@aliyun-1 -n 50 --no-pager
```

窗口关闭时执行器会显示“没有工作”（WINDOW_CLOSED），属于正常现象。**真正连 StarRocks 要等第一次开窗**，所以 SR 连通性和账号权限问题，通常在第一次范围发现之后才暴露（见 6.3）。

### 4.4 清理

```bash
rm -rf /tmp/srdq-offline-${VERSION} /tmp/srdq-offline-${VERSION}-alinux4-x86_64.tar.gz*
```

### 4.5 安装后的目录

| 路径 | 内容 | 权限 |
|---|---|---|
| `/opt/srdq/releases/<版本>/` | 应用代码、venv、`config-snapshot/` | root |
| `/opt/srdq/current` | 指向当前版本的符号链接 | |
| `/opt/srdq/postgresql/<版本>/`、`/opt/srdq/postgresql/current` | PostgreSQL 二进制 | |
| `/opt/srdq/deploy/` | `install.sh`、`upgrade.sh`、`rollback.sh`、`lib.sh` | |
| `/opt/srdq/bin/srdq-pg-backup` | 备份脚本 | |
| `/etc/srdq/config.yaml` | 生产配置 | root:srdq 0640 |
| `/etc/srdq/secrets/<cluster-id>.json` | 六个物理集群各自的 SR 凭证 + 执行器令牌 | 对应执行器用户 0600 |
| `/etc/srdq/secrets/pg.json` | 控制库连接串（无密码，走 Unix socket） | srdq-ctl 0600 |
| `/var/lib/srdq/pg/` | 控制库数据 | srdq-pg |
| `/var/lib/srdq/backups/` | 控制库备份（`*.dump`） | |
| `/var/lib/srdq/reports/` | 日报和阶段报告 | |
| `/var/lib/srdq/controller/`、`/var/lib/srdq/executor/<cluster-id>/` | controller 和六个 executor 的独立数据目录 | |
| `/var/lib/srdq/upgrades/` | 升级状态记录 | |

**代码在 `/opt`，数据在 `/var/lib/srdq`。** 升级和回滚只替换代码与配置，数据保留。

## 5. 访问 Web 控制台

在浏览器打开 **http://<ECS IP>:8470/**。

## 6. 首次上线全流程（从零到第一份日报）

### 6.0 时间线总览

范围发现只在执行窗口内运行，所以首次上线**至少跨两个晚上**：

| 时间 | 操作人 | 操作 | 章节 |
|---|---|---|---|
| 第 1 天白天 | 运维 | 安装部署、检查 | 第 4 章 |
| 第 1 天白天 | 使用人员 | 导入 `assets.csv` 并确认 | 6.1 |
| 第 1 天白天 | 使用人员 | 点“开始发现”，排队等开窗 | 6.2 |
| 第 1 天晚上 20:00 起 | 自动 | 每个资产所属校验组的两个执行器读取表结构和分区 | 6.2 |
| 第 2 天上午 | 使用人员 | 检查并确认范围清单 | 6.3 |
| 第 2 天上午 | 使用人员 | 导入全部 METRIC、SAMPLE 规则并确认 | 6.4 |
| 第 2 天上午 | 使用人员 | 批量批准规则 | 6.5 |
| 第 2 天上午 | 使用人员 | 创建计划和周期 | 6.6、6.7 |
| 第 2 天晚上 20:00 起 | 自动 | 第一轮校验 | 6.8 |
| 第 3 天 08:15 后 | 使用人员 | 查看第一份日报 | 6.9 |

> 如果资产很多（例如数仓集群 3475 张表），第一次发现在一个窗口内可能跑不完，没跑完的部分会在下一个窗口继续。第 2 天上午先到“范围清单”页确认发现是否已完成：完成后才会出现草稿清单。

### 6.1 导入资产清单

**方式一：Web（推荐）**

1. 打开“导入”页面，类型选“资产清单（ASSET_LIST）”，模式保持默认的 `CREATE_OR_VALIDATE`，选择对应校验组目录下的 `assets.csv`，点“预览”。
2. 在预览页核对：
   - 总行数应等于文件行数，例如数仓校验组为 3475。
   - 每行 `pair_id` 都是预期校验组，SOURCE/TARGET 库表名正确。
   - 状态统计中应全部是“新建”，ERROR 为 0。
   - 如果有 ERROR，查看每行的错误信息（例如校验组不存在、层级拼写、库表名为空、重复行），修正文件后重新预览。
3. 填写原因，例如“首次导入数仓集群资产”，点“确认”。

确认后：

- 每张表成为一个资产，并**自动生成并批准**一条 `baseline_count`（COUNT）规则。
- ERROR 行不会生效，其余行照常写入。

**方式二：命令行**

```bash
# CSV 必须能被 srdq-ctl 读取
install -m 0644 assets.csv /tmp/srdq-assets.csv
srdq import assets /tmp/srdq-assets.csv                                   # 只预览，打印统计
srdq import assets /tmp/srdq-assets.csv --confirm --reason "首次导入资产"   # 预览并确认；有 ERROR 行时拒绝确认
```

导入模式说明：

| 模式 | 用途 |
|---|---|
| `CREATE_OR_VALIDATE`（默认） | 新表直接创建；已存在且内容相同的表记为“未变化”；已存在但内容不同（如改了优先级）的表记为 ERROR，防止误覆盖 |
| `UPDATE_EXPLICIT` | 明确要修改已有资产，例如改优先级、改启用状态 |

### 6.2 范围发现

范围发现会让每个资产所属校验组的 SOURCE/TARGET 执行器分别读取表结构和分区信息，生成“范围清单”，即每张表要按哪些分区来校验。

1. 打开“范围清单”页，点击“开始发现”，并填写原因。
2. 页面会出现一个发现运行。白天它显示为排队状态，**20:00 开窗后才真正执行**。
3. 同一时间只能有一个发现运行。重复点击会提示 `DISCOVERY_RUNNING`。

每张表在所属校验组的两端各生成一个元数据任务，所有任务结束后，系统自动生成一个**草稿（DRAFT）清单**。

> 想提前验证 SR 连通性和权限：可以只导入几张表，在开窗时段（20:00–次日 08:00）点“开始发现”，几分钟后就能看到结果。确认无误后再导入全量。

### 6.3 检查并确认范围清单

打开“范围清单”页，进入最新的 DRAFT 清单。

**先看摘要：**

| 字段 | 说明 |
|---|---|
| assets | 参与发现的表数 |
| entries | 生成的范围条目数，一张分区表按分区展开为多条 |
| by_reason | 按原因统计的条目数，见下表 |
| incomplete_assets | 元数据未知或无权限的表 |
| inventory_complete | 全部表的元数据都已拿到时为 true |

**再看条目原因（expected_reason）：**

| 原因 | 含义 | 处理建议 |
|---|---|---|
| `IN_SCOPE` | 两端都有，正常参与校验 | 无需处理 |
| `SOURCE_ONLY` | 分区只在华为侧存在 | 通常是同步遗漏或延迟，记录下来跟进 |
| `TARGET_ONLY` | 分区只在阿里侧存在 | 通常是阿里侧多建或历史残留，跟进 |
| `TABLE_ABSENT` | 至少一端没有这张表 | 确认库表名是否正确、是否导错集群 |
| `ACCESS_DENIED` | 只读账号没有权限 | 联系 DBA 给只读账号授权，之后重新发现 |
| `UNKNOWN`（INVENTORY_BLOCKER） | 元数据查询失败（超时、连接失败等） | 查看执行器日志，修复后重新发现 |
| `DISAPPEARED` | 上一版清单里有，这次没找到 | 分区被删除或过期属于正常；否则需要跟进 |

范围类型（scope_kind）说明：

- RANGE 或 LIST：按分区校验。
- ALL：整表一个范围，用于非分区表或分区列不可用的表。
- NULL_SCOPE：分区列允许为空时，额外校验分区列为 NULL 的行。

**确认清单：** 检查没有问题，或者问题已经记录在案后，填写原因并点“确认”。

- 新确认的清单会取代上一版 CONFIRMED 清单。
- 只有已确认的清单才能用于计划运行。
- 少量 `UNKNOWN` 或 `ACCESS_DENIED` 不影响确认；这些表会显示为不完整或阻塞，其余表照常校验。
- 如果大面积是 `TABLE_ABSENT` 或 `UNKNOWN`，**不要确认**。点“驳回”，先排查连通性、账号和是否导错集群。

### 6.4 导入 METRIC 与 SAMPLE 规则

> 前提：至少已有一版 DRAFT 或 CONFIRMED 清单，也就是第一次发现已经完成。否则所有行都会报 `NO_METADATA: run discovery first`。规则里引用的表必须已经作为资产导入，否则报 `ASSET_NOT_FOUND`。

逐个文件导入：

1. 打开“导入”页面，类型选“METRIC 规则模板”或“SAMPLE 规则模板”，上传一个文件，例如 `metric_rules_ods.csv`，点“预览”。
2. 预览结果每行一个状态：

   | 状态 | 含义 |
   |---|---|
   | OK | 校验通过，确认后生成 DRAFT 规则 |
   | UNSUPPORTED | 能登记，但当前不能执行，例如列类型不支持或两端类型不一致；原因显示在 support_reason。**不能批准** |
   | ERROR | 不会生效，例如列不存在、表未导入、格式错误 |

3. 填写原因并点“确认”。ERROR 行被跳过，其余行生效。
4. 对三个校验组目录下的每个 `metric_rules_*.csv` 和 `sample_rules_*.csv` 重复以上步骤，并核对每行 `pair_id`。

命令行等价写法（有 ERROR 行时 CLI 会拒绝确认，适合严格模式）：

```bash
for f in metric_rules_*.csv; do
  install -m 0644 "$f" "/tmp/srdq-$f"
  srdq import metric "/tmp/srdq-$f" --confirm --reason "首次导入 $f"
done
for f in sample_rules_*.csv; do
  install -m 0644 "$f" "/tmp/srdq-$f"
  srdq import sample "/tmp/srdq-$f" --confirm --reason "首次导入 $f"
done
```

注意：

- 预览之后、确认之前，如果数据有变化（例如期间又完成了一次发现），确认会提示 `PREVIEW_STALE`，重新预览即可。
- 同一张表、同一个 rule_key 再次导入不同内容时，会生成**新版本**的 DRAFT 规则。新版本批准后，旧版本自动变为 SUPERSEDED。
- 导入同样内容不会产生新版本。

### 6.5 批准规则

导入的规则都处于 DRAFT 状态，**批准后才会进入运行**。

**少量规则：Web 批准**

1. 打开“规则”页，筛选“状态 = DRAFT”、“能力 = SUPPORTED”。
2. 勾选要批准的规则。“审批依据”可以留空，留空时使用全局默认的“免审批”。
3. 点“批准勾选的规则”。

每页最多 200 条，页面没有“全选”。规则数以千计时，请用下面的脚本。

**大量规则：在 ECS 上用脚本批量批准**

把下面的脚本保存为 `/tmp/approve_drafts.py`。它只调用本机 REST API，不需要任何凭证：

```python
import json
import sys
import urllib.request

BASE = "http://127.0.0.1:8470/v1"
REASON = sys.argv[1] if len(sys.argv) > 1 else "批量批准导入的规则"
KIND = sys.argv[2] if len(sys.argv) > 2 else ""          # 可选：METRIC 或 SAMPLE


def call(method, path, body=None):
    data = None if body is None else json.dumps(body).encode()
    req = urllib.request.Request(BASE + path, data=data, method=method,
                                 headers={"Content-Type": "application/json"})
    with urllib.request.urlopen(req, timeout=300) as r:
        return json.load(r)


done = 0
while True:
    q = "/check-rules?status=DRAFT&support_state=SUPPORTED&page=1&page_size=200"
    if KIND:
        q += "&kind=" + KIND
    page = call("GET", q)
    ids = [r["id"] for r in page["items"]]
    if not ids:
        break
    out = call("POST", "/check-rules/approve", {"rule_ids": ids, "reason": REASON})
    done += sum(1 for r in out["rules"] if r["changed"])
    print(f"已批准 {done}，剩余 {page['total'] - len(ids)}", flush=True)
print("完成，共批准", done)
```

执行：

```bash
python3.11 /tmp/approve_drafts.py "首次上线批准数仓集群规则"            # 批准全部 DRAFT 且 SUPPORTED 的规则
python3.11 /tmp/approve_drafts.py "首次上线批准 METRIC" METRIC          # 只批准 METRIC
```

批准后核对：

```bash
# DRAFT 且 SUPPORTED 的剩余数应为 0
curl -s 'http://127.0.0.1:8470/v1/check-rules?status=DRAFT&support_state=SUPPORTED&page_size=1' \
  | python3.11 -c 'import json,sys; print(json.load(sys.stdin)["total"])'
# 查看有多少 UNSUPPORTED 规则（这些不会执行，可在规则页查看原因）
curl -s 'http://127.0.0.1:8470/v1/check-rules?support_state=UNSUPPORTED&page_size=1' \
  | python3.11 -c 'import json,sys; print(json.load(sys.stdin)["total"])'
```

批准动作会逐条写入审计日志，可以在“审计”页查看。

### 6.6 创建计划

计划定义“用哪版清单、校验哪些表、做哪些档位”。打开“计划”页，在“新建计划”中填写：

| 字段 | 建议 |
|---|---|
| 名称 | 例如“数仓集群-每日全量” |
| 范围清单 | **每次用最新确认的清单**（LATEST_CONFIRMED）。选“固定”则永远只用指定的那一版 |
| 校验组 | 可选择一个、多个或全部校验组；只会纳入所选组的资产 |
| 检查类型 | 勾选 COUNT、METRIC、SAMPLE；不勾选等于全部（不含 DEEP） |
| rule_key | 留空表示全部规则；也可以只填 `amount_totals` 等 |
| 层级 / 资产 ID | 留空表示所选校验组的全部资产；也可以只勾选 ODS 等层级，或只填指定资产 ID |

推荐的常见组合：

- **一个全量计划**：选择全部校验组、全部资产、全部档位，每天跑一轮。
- 如果夜间窗口跑不完全量，可以拆分：
  - “核心层快检”：COUNT + METRIC，每日运行。
  - “全量抽样”：SAMPLE，连续滚动运行。

计划详情页的“立即运行”会马上创建一轮运行。运行在创建时**冻结**当时的规则版本和范围清单，之后批准的新规则或确认的新清单不影响这一轮。运行同样要等开窗才会执行。

### 6.7 创建周期（自动运行）

打开“周期”页，在“新建周期”中填写：

| 字段 | 说明 |
|---|---|
| 计划 | 选择上一步的计划 |
| 类型 | `CRON`：按 5 段 CRON 触发，例如 `5 0 * * *` 表示每天 00:05<br>`INTERVAL`：固定间隔，最少 60 秒<br>`CONTINUOUS`：上一轮结束后休息 N 秒（最少 60，默认 300）再开下一轮，适合想让检查尽量连续滚动的场景 |
| 时区 | 默认 Asia/Shanghai |
| 开始 / 结束 | 可空；ISO 时间，例如 `2026-10-12T00:00:00+08:00` |
| 重叠时 | `SKIP`：上一轮没跑完就跳过本次<br>`COALESCE`：合并为一次 |
| 错过触发时 | `SKIP`：错过就不补<br>`LATEST`：只补最近一次 |
| 到结束时间时取消在途运行 | 勾选后，到“结束”时间时取消还没跑完的运行 |

先点“预览下次触发时间”核对，再点“创建”。

推荐配置：

- 每日全量：`CRON` + `5 0 * * *` + 重叠 `SKIP`，每天开窗后 5 分钟创建一轮。上一轮如果没跑完（跨窗口继续），当天就跳过。
- 滚动连续：`CONTINUOUS` + 休息 300 秒。

周期详情页可以执行：

- 停用（DISABLE）、启用（ENABLE）、归档（ARCHIVE）。
- 重启（RESTART）：重新计算下次触发时间。

### 6.8 第一轮运行时观察

开窗后（20:00 以后），可以在看板或运行页观察：

- **看板**：
  - 在途运行和每个档位的进度（总数、已完成、相等、不同、不完整）。
  - 六个物理集群 × 五类池的 READY 数、最老队龄、live/limit、最近一小时完成量、时延、成功率、超时率和 ETA。
  - 负载与超时告警。
- **运行详情**（`/runs/<id>`）：
  - 节点表：按表和分区展示，可按层级、库表名筛选。
  - 检查表：按检查展示，可按档位、覆盖状态筛选。
  - 每行都有控制按钮，见 7.3。

第一晚建议有人值守到 01:00 左右，确认：

- 六个集群执行器都在领取工作。可以看“执行器”页的心跳，或看看板上的 live 数。
- COUNT、METRIC、SAMPLE 能同时推进，没有长期 READY 却不领取的池。
- 没有大量 ERROR 或持续的超时、变慢告警，六个 StarRocks 集群负载在可接受范围内。

### 6.9 查看第一份日报

每天 08:00 关窗，**08:15 左右**自动生成当天日报。打开“报告”页即可查看或下载：

| 文件 | 内容 |
|---|---|
| `report.md` | 汇总：覆盖率、结论、新增或持续或已解决的差异、不完整项、负载情况 |
| `progress.csv` | 各运行、各档位的进度 |
| `differences.csv` | 差异明细（值默认脱敏） |
| `incomplete.csv` | 未完成或无法下结论的检查及原因 |
| `load.csv` | 六个物理集群各类型池的负载、时延和超时监控记录 |

报告文件同时保存在 ECS 的 `/var/lib/srdq/reports/<report_id>/` 下。

## 7. 日常使用

### 7.1 每日例行（建议 08:30 后）

1. **看板**：
   - 是否有 CRITICAL 或 WARN 告警。
   - 各集群各类型池的超时率、P95 和最老 READY 队龄是否异常。
   - 是否有运行长时间不前进，预计完成时间是否超出窗口。
2. **报告**：阅读当天日报的 `report.md`，重点看新增差异（NEW）和不完整项。
3. **差异**：对 NEW 和 PERSISTENT 的差异逐一定位，处理流程见 8.3。
4. **范围清单**：如果昨晚执行过发现，确认新的 DRAFT 清单（见 7.2）。

### 7.2 定期重新发现（让新分区进入校验）

每次发现会生成一版清单，新分区（例如每天新增的日分区）**只有在新的发现完成并确认后**，才会被计划纳入。当前配置为 `new_scope_policy: REQUIRE_CONFIRM`，每版清单都需要人工确认。

推荐节奏如下：

- 每天上午确认昨晚的 DRAFT 清单，然后点“开始发现”，排队到当晚执行。
- 当天检查范围的变化：
  - 新增分区显示为 `is_new`，表示新出现的条目。
  - 已删除的分区显示为 `DISAPPEARED`。
- 确认后，使用“最新确认清单”的计划，在下一轮运行时自动纳入新分区。

这样，第 D 天新出现的分区，会在第 D+1 晚被发现，第 D+2 晚被校验。

> 如果希望兼容的新分区自动纳入、免去每日确认，需要把配置 `scope.new_scope_policy` 改为 `AUTO_ADD_COMPATIBLE`。修改配置需要研发重新打包并升级，见 9.8。

### 7.3 控制运行（暂停、取消、优先级、窗口）

所有控制都是“预览 → 执行”两步。执行时要填写原因，状态有变化则要求重新预览。

**作用对象：**

| 对象 | 位置 | 含义 |
|---|---|---|
| 整轮运行（RUN） | 运行详情页顶部“整轮控制” | 影响整轮 |
| 范围节点（RANGE_NODE） | 运行详情页的节点表 | 某张表的某个分区 |
| 单项检查（RUN_CHECK） | 运行详情页的检查表 | 某条规则在某个范围上的检查 |

**可用操作：**

| 操作 | 说明 |
|---|---|
| PAUSE / RESUME | 暂停或恢复。暂停后不再开始新的观察，已开始的会收尾 |
| CANCEL | 取消，不可恢复 |
| ARCHIVE / RESTORE | 归档或恢复显示 |
| SET_PRIORITY / CLEAR_PRIORITY | 设置优先级（0–100）或清除临时优先级 |
| START | 启动一轮还未开始的运行 |
| REGENERATE | 按当前规则和清单重新生成这轮运行或这项检查，例如修复问题后重跑 |

“效果范围”：

- CURRENT_ONLY：只影响这一轮。
- THIS_AND_FUTURE：只用于节点和检查，对以后的运行也生效，例如永久暂停某张有问题的表。

THIS_AND_FUTURE 生成的长期策略可以在资产详情页的“策略”中查看。

**窗口控制（看板页，仅在开窗时可用）：**

- **延长窗口**：
  - 按分钟（1–1440）或指定截止时间延长。
  - 最多延长 24 小时，不能进入下一个窗口的开窗时间。
  - 适用场景：例如业务确认早上可以多跑一小时。
- **提前关闭窗口**：立即进入关窗流程，取消在途查询。适用场景：例如源端临时有大促或重要任务。

窗口关闭时点这两个按钮会提示 `WINDOW_CLOSED`。

### 7.4 新增、修改、下线表或规则

| 场景 | 操作 |
|---|---|
| 新增表 | 把新表追加进 assets.csv（或单独做一个只含新表的 CSV），按默认模式导入 → 重新发现 → 确认清单 → 导入这些表的规则 → 批准 |
| 修改优先级或启用状态 | 修改 CSV 后选 `UPDATE_EXPLICIT` 模式导入 |
| 临时不校验某张表 | 方法一：资产 `enabled=false`，用 `UPDATE_EXPLICIT` 导入<br>方法二：在运行页对节点做 PAUSE，效果选 THIS_AND_FUTURE |
| 停用某条规则 | “规则”页下方的“启用 / 停用”。停用只影响新的运行，已冻结的运行不受影响 |
| 修改规则 | 修改 CSV 后重新导入 → 生成新版本 DRAFT → 批准后旧版本自动 SUPERSEDED |
| 表结构变化（加列、改类型） | 重新发现并确认清单；必要时重新生成并导入规则 |

### 7.5 手工复核与 DEEP 深度比对

发现差异后，如果需要重新比对，或想做更细的逐行比对，可以发起手工复核。

**入口：**

- 方式一：在比较结果页（从差异列表点进去）直接发起，会自动带上资产和来源比较。
- 方式二：在“手工复核”页新建。

**填写项：**

| 字段 | 说明 |
|---|---|
| 资产 ID | 资产详情页地址中的 ID |
| 来源比较 ID | 可空。从比较结果页发起时会自动填写 |
| 类型 | COUNT、METRIC、SAMPLE 表示用现有规则重新比对；DEEP 表示深度比对 |
| rule_key | 可空 |
| scope_keys | 每行一个范围键（可在清单或运行页查到）。不填则按来源比较的范围，或整表 |
| DEEP 列 | 逗号分隔；不填表示全部共同列 |
| DEEP 方式 | `HASH_BUCKET` 按哈希分桶；`KEY_RANGE` 按主键区间，需要填写区间 JSON |
| 桶数、每端最大行数、最大读取字节 | 限制深度比对的规模，避免对源端造成压力 |
| 明细审批依据 | 需要查看或外传明细值时填写 |
| 原因 | 必填 |

**流程：** 预览 → 核对将要比对的范围和规模 → 确认 → 系统生成一轮复核运行，同样在开窗时执行 → 在运行页和差异页查看结果。

## 8. 结果解读

### 8.1 覆盖状态（coverage_state）

每项检查在一轮运行中的最终状态：

| 状态 | 含义 |
|---|---|
| PENDING | 尚未执行或执行中 |
| COMPLETED_EQUAL | 已完成，两端一致 |
| COMPLETED_DIFFERENT | 已完成，两端不一致，会产生差异记录 |
| INCONCLUSIVE | 无法下结论，例如观察期间数据在变化，或两端读到的数据不可比 |
| ERROR | 执行出错，例如超时、SQL 错误、连接失败 |
| UNSUPPORTED | 规则不能在该范围上执行，例如类型不支持 |
| BLOCKED | 被阻塞，例如元数据未知（INVENTORY_BLOCKER）或权限不足 |
| EXCLUDED | 按清单排除，不计入总数 |

看板和报告里的“不完整”是 ERROR、INCONCLUSIVE、UNSUPPORTED、BLOCKED 四种状态的合计。这些检查**没有给出结论**，不能视为“一致”。

### 8.2 差异的持续状态

| 状态 | 含义 |
|---|---|
| NEW | 这一组检查第一次出现不一致 |
| PERSISTENT | 连续多次比对都不一致 |
| RESOLVED | 之前不一致，最近一次比对恢复一致 |

差异页可以按档位、层级、持续状态和库表名筛选。

差异中的具体值（分组值、主键值、两端值）**默认脱敏**，显示为 `••••`。需要看原值时，在比较结果页（从差异列表点进去）点“显示原值”，地址会带上 `show_values=1`。查看原值的操作会留在浏览器历史中，请遵守数据外传规定。原值只保留 `retention.raw_value_days` 天（默认 7 天），之后会在窗口外自动清理。

### 8.3 差异处理建议流程

1. **先看档位**：
   - COUNT 不同：分区行数不同，最常见，通常是同步延迟或遗漏。
   - METRIC 不同：行数相同但聚合值不同。
   - SAMPLE 不同：具体某些行的列值不同。
2. **再看是否持续**：
   - NEW：可能是夜间同步时点不一致造成的。建议等下一轮，或发起一次手工复核重新比对。
   - PERSISTENT：大概率是真实差异，需要交给数据同步负责人排查。
3. **定位范围**：在比较结果页查看具体分区、分组和主键桶。必要时发起 DEEP 深度比对，定位到具体行。
4. **修复后验证**：同步侧修复后，可以等下一轮自动比对，也可以发起手工复核。恢复一致后，差异变为 RESOLVED。

### 8.4 阶段报告

在“报告”页填写开始日期和结束日期，生成阶段报告，汇总这段时间的覆盖与差异，适合周报或里程碑汇报。

日报内容不对时（例如当晚进行了恢复操作），可以在报告页对该日“重新生成”。

命令行等价写法：

```bash
srdq report stage --start 2026-10-01 --end 2026-10-07 --reason "第一周阶段报告"
srdq report regenerate-daily 2026-10-08 --reason "恢复后重新生成"
```

## 9. 日常运维

### 9.1 服务管理

```bash
# 查看全部
systemctl status 'srdq-*' --no-pager

# 重启应用服务（不包括数据库）
sudo systemctl restart srdq-controller srdq-web 'srdq-executor@*.service'

# 停止或启动数据库（会影响全部应用服务，谨慎操作）
sudo systemctl stop srdq-controller srdq-web 'srdq-executor@*.service'
sudo systemctl restart srdq-pg
sudo systemctl start srdq-controller srdq-web 'srdq-executor@*.service'
```

注意事项：

- **窗口内重启执行器**：在途查询会中断。controller 会通过租约超时（约 120 秒）回收这些工作并重试。没有必要时，避免在窗口内重启。
- 所有服务都已 `enable`，ECS 重启后会自动拉起。

### 9.2 日志

所有日志都写入 journald：

```bash
journalctl -u srdq-controller -f                      # 实时跟踪
journalctl -u srdq-executor@huawei-1 --since "yesterday 20:00" --no-pager
journalctl -u srdq-executor@aliyun-1 --since "today" -p warning --no-pager
journalctl -u srdq-web -n 200 --no-pager
journalctl -u srdq-pg -n 100 --no-pager
journalctl -u srdq-pg-backup --since "-2 days" --no-pager
```

其余实例把 `huawei-1` / `aliyun-1` 替换为对应 `cluster_id`。

### 9.3 健康巡检

```bash
srdq status                                   # 控制状态、窗口、集群、告警、在途运行
curl -s http://127.0.0.1:8470/v1/health       # Web 和数据库是否正常，schema 版本
curl -s http://127.0.0.1:8470/v1/workers | python3.11 -m json.tool    # 执行器心跳
curl -s 'http://127.0.0.1:8470/v1/incidents' | python3.11 -m json.tool | head -50
df -h /var/lib/srdq
sudo ls -lh /var/lib/srdq/backups | tail      # 备份目录为 srdq-pg 0700，需要 sudo
```

### 9.4 备份

- **自动备份**：
  - `srdq-pg-backup.timer` 每天 02:30 左右执行，保留 14 天。
  - 备份文件为 `/var/lib/srdq/backups/<UTC时间>-<label>.dump`，PostgreSQL custom 格式。
- **手动备份**：

  ```bash
  sudo /opt/srdq/bin/srdq-pg-backup --label manual
  # 输出备份文件路径
  ```

- 建议定期把 `/var/lib/srdq/backups/` 下最新的 dump **复制到 ECS 以外**的受控存储，防止整机故障。
- 备份只包含控制库，包括资产、规则、清单、结果、审计等。**不包括 SR 凭证**，凭证在离线包里。

### 9.5 磁盘与数据保留

| 内容 | 位置 | 增长 | 清理 |
|---|---|---|---|
| 控制库 | `/var/lib/srdq/pg` | 随运行结果持续增长 | 原始值按 `raw_value_days` 自动清理，汇总结果保留 |
| 备份 | `/var/lib/srdq/backups` | 每天一个 | 自动保留 14 天 |
| 报告 | `/var/lib/srdq/reports` | 每天一份 | 不自动清理，按需归档 |
| 升级前备份 | `/var/lib/srdq/backups/*-pre-*.dump` | 每次升级一个 | 和普通备份一样按保留期清理；需要长期保留的请另外复制 |

看板上的 `purge_deferred` 表示等待清理的原值数量，这些数据会在窗口外清理。

### 9.6 负载与吞吐监控

系统只监控和告警，不会自动降低并发、跨池借用并发或自动停止集群派发。每个物理集群的五类并发都来自 `physical_clusters[].concurrency`，最低为 1，没有额外的集群总并发上限。

看板按“物理集群 × 类型池”展示：

- `ready`、最老 READY 队龄和 `live/limit`。
- 最近一小时完成量和每小时速率。
- avg、P50、P95、max 时延。
- 成功率、超时率和按当前速率估算的 ETA。

出现超时率或变慢告警时：

1. 先确认对应 StarRocks 集群的负载、FE 状态和网络。
2. 根据具体类型池判断影响；COUNT 拥堵不会阻止 METRIC、SAMPLE 等其他池领取。
3. 如需调整并发，修改该物理集群对应类型的显式并发值，重新构建离线包并升级。系统不会自动替你调整。
4. 如需立即止损，可以暂停运行、节点或检查，或提前关闭窗口。

### 9.7 执行器管理

- “执行器”页可以查看六个物理集群执行器的注册信息、所属 `cluster_id`、最后心跳和能力自检。
- 执行器令牌由安装脚本生成，并写在对应物理集群的凭证文件里。升级会保留已有令牌。
- “停用执行器”会让该执行器无法再领取工作。**除非确认令牌泄露，否则不要停用**；停用后需要研发协助重新签发令牌。

### 9.8 修改配置或数据库密码

配置和凭证都打包在离线包里，**生产机上不要手工编辑** `/etc/srdq/config.yaml` 或凭证文件：下次升级时，包内配置会覆盖它们。

需要修改窗口时间、并发、SR 账号密码等内容时，流程如下：

1. 把修改需求提交给研发。研发修改 provision 配置，递增版本号，重新构建离线包。
2. 运维按第 10 章执行升级。升级会写入新配置，同时保留已有的执行器令牌。

## 10. 升级

### 10.1 升级前

- [ ] 拿到新版本离线包和 `.sha256` 文件，并确认版本号比当前版本**高**。可用 `readlink /opt/srdq/current` 查看当前版本。
- [ ] 选在**窗口关闭时段**升级，建议 09:00–19:00，避免中断夜间校验。
- [ ] 确认当前没有人在 Web 上进行导入或确认操作。
- [ ] 记录当前版本号，回滚时要用。

### 10.2 执行升级

```bash
cd /tmp
VERSION=<新版本>
sha256sum -c "srdq-offline-${VERSION}-alinux4-x86_64.tar.gz.sha256"
tar xzf "srdq-offline-${VERSION}-alinux4-x86_64.tar.gz"
sudo "./srdq-offline-${VERSION}/deploy/upgrade.sh"
```

升级脚本依次执行：

1. 检查已安装，且新版本与当前版本不同。PostgreSQL 主版本变化需要专门的迁移，脚本会拒绝。
2. 安装新版本代码到 `/opt/srdq/releases/<新版本>`。
3. 记录当前在运行的服务，保存旧版本配置快照，停止应用服务。
4. **执行升级前备份**：`/var/lib/srdq/backups/<时间>-pre-<新版本>.dump`。
5. 安装新的 systemd 单元和包内配置。已有的执行器令牌会保留。
6. 执行数据库增量迁移。
7. 原子切换 `/opt/srdq/current`，恢复升级前在运行的服务，并打印状态。

成功时会打印：

```text
upgraded <旧版本> -> <新版本>
backup: /var/lib/srdq/backups/<...>-pre-<新版本>.dump
rollback: /opt/srdq/deploy/rollback.sh <旧版本> /var/lib/srdq/backups/<...>.dump
```

**请把这三行保存下来。**

失败时的情况：

- **迁移之前**失败：脚本自动恢复旧版本并重启服务，系统回到升级前状态。根据错误信息修正后重试即可。
- **迁移之后**失败：保留新版本，并打印备份路径和回滚命令。可以根据错误排查，也可以按第 11 章回滚。

### 10.3 升级后检查

与 4.3 相同。另外需要确认：

```bash
readlink /opt/srdq/current                     # 指向新版本
curl -s http://127.0.0.1:8470/v1/health        # schema_version 已更新
srdq status
```

然后在 Web 上查看看板、计划、周期是否正常，当晚确认运行照常进行。

最后清理 `/tmp` 下的安装包和解压目录。

## 11. 回滚

只有在升级后发现严重问题时才回滚。回滚会把**数据库恢复到升级前的备份**，升级之后产生的数据（新的结果、导入、确认等）会丢失。回滚前，脚本会再做一次安全备份。

```bash
sudo /opt/srdq/deploy/rollback.sh <旧版本> /var/lib/srdq/backups/<升级前备份>.dump
```

- 参数直接使用升级时打印的 rollback 命令。
- 备份文件必须位于 `/var/lib/srdq/backups/`。

回滚脚本依次执行：

1. 对当前数据库做安全备份。
2. 删除并重建控制库，然后从指定 dump 恢复。
3. 恢复旧版本的配置快照，把 `current` 切回旧版本。
4. 进入 **RECOVERY 模式**，重启服务。

回滚完成后，**必须确认恢复**才能恢复调度，见 12.2。

## 12. 备份、恢复与 RECOVERY 模式

### 12.1 什么是 RECOVERY 模式

从备份恢复数据库之后，控制库里记录的“在途查询、租约、取消请求”和实际情况可能不一致。为了避免重复派发或误判，系统会进入 RECOVERY 模式：

- 执行器领取工作时会收到 503 RECOVERY，不派发任何工作。
- 看板显示 RECOVERY 状态。

### 12.2 确认恢复

1. 确认六个集群执行器都在线：查看“执行器”页，或 `systemctl status 'srdq-executor@*.service'`。
2. 查看看板上是否有“未确认的取消”（cancel_unconfirmed）。必要时到 StarRocks 上确认对应查询已经结束。
3. 确认恢复，可以任选一种方式：
   - Web：看板页点“确认恢复（预览）”，执行时填写原因。
   - 命令行：

     ```bash
     srdq recovery confirm --reason "回滚到 <旧版本>，已核对执行器状态"
     ```

4. 确认后系统恢复调度。如果恢复影响了某天的日报，可以对那天重新生成日报（见 8.4）。

### 12.3 手工从备份恢复（整机故障或误操作）

> 下面的命令会删除并重建控制库，请先和研发确认再执行。
>
> `rollback.sh` 只能切换到**另一个**已安装版本，对当前版本会提示 `already active`。在当前版本上恢复备份，请按下面的步骤手工操作。

```bash
PG_BIN=/opt/srdq/postgresql/current/pgserver/pginstall/bin
DUMP=/var/lib/srdq/backups/<要恢复的>.dump      # 必须是 srdq-pg 可读的 custom 格式 dump

# 1. 停止应用服务，数据库保持运行
sudo systemctl stop srdq-controller srdq-web 'srdq-executor@*.service'

# 2. 先对当前库做一次安全备份，并记下打印的路径
sudo /opt/srdq/bin/srdq-pg-backup --label before-restore

# 3. 校验 dump，然后重建库并恢复
sudo runuser -u srdq-pg -- "$PG_BIN/pg_restore" --list "$DUMP" >/dev/null && echo dump ok
sudo runuser -u srdq-pg -- "$PG_BIN/dropdb" -h /run/srdq-pg --force --if-exists srdq
sudo runuser -u srdq-pg -- "$PG_BIN/createdb" -h /run/srdq-pg --owner=srdq-ctl srdq
sudo runuser -u srdq-pg -- "$PG_BIN/pg_restore" -h /run/srdq-pg --exit-on-error --no-owner \
  --role=srdq-ctl --dbname=srdq "$DUMP"

# 4. 进入 RECOVERY，再启动服务
srdq recovery enter --reason "从备份 $(basename "$DUMP") 恢复"
sudo systemctl start srdq-controller srdq-web 'srdq-executor@*.service'
```

然后按 12.2 确认恢复。

第 3 步失败时，用第 2 步的安全备份执行同样的命令，即可恢复到操作前的状态。

如果是在新机器上整机重建：

1. 用**同版本**离线包完成第 4 章的安装。
2. 把备份 dump 复制到新机的 `/var/lib/srdq/backups/`，并执行 `sudo chown srdq-pg:srdq-pg <dump>`、`sudo chmod 0600 <dump>`。
3. 执行上面的第 1–4 步。

## 13. 故障排查

### 13.1 安装和升级

| 现象 | 原因 | 处理 |
|---|---|---|
| `sha256sum -c` 显示 FAILED | 传输损坏 | 重新传输 |
| `Python 3.11 is required` / `venv module is required` | 缺少 Python 3.11 | `dnf install python3.11` |
| `glibc 2.17 or newer is required` | 系统过旧 | 更换为 Alibaba Cloud Linux 4 |
| `bundle targets x86_64, host is aarch64` | 架构不符 | 使用 x86_64 机器 |
| `bump project.version` | 同版本号不同内容 | 让研发递增版本重新打包 |
| 升级提示 `version X is already active` | 新包和当前版本相同 | 确认包是否正确 |
| `another deployment or backup is in progress` | 另一个 install、upgrade、rollback 或备份（包括 02:30 的定时备份）正在运行 | 稍等几分钟后重试；确认没有残留进程 |
| controller 或 web 启动失败，日志说能读取 SR 凭证 | 凭证文件权限被改动 | 不要手工改 `/etc/srdq/secrets` 的权限；用同版本包重新执行升级或安装恢复权限，或联系研发 |

### 13.2 访问

| 现象 | 原因 | 处理 |
|---|---|---|
| 浏览器打不开 `http://<ECS IP>:8470` | 安全组未放行 8470，或 srdq-web 没有运行 | 检查安全组入方向规则；在 ECS 上执行 `systemctl status srdq-web` 和 `curl -s http://127.0.0.1:8470/v1/health` |
| web 监听地址仍是 127.0.0.1 | `/etc/srdq/config.yaml` 里 `web.bind_address` 写的是 `127.0.0.1` | 改为 `0.0.0.0` 后 `sudo systemctl restart srdq-web`；`ss -ltn \| grep ':8470 '` 确认 |
| 页面 500 INTERNAL | 程序内部错误 | 查看 `journalctl -u srdq-web`，把报错发给研发 |

### 13.3 使用

| 现象 | 原因 | 处理 |
|---|---|---|
| 点了“开始发现”或“立即运行”，一直不动 | 窗口关闭，或执行器离线 | 白天不动是正常的，等 20:00；开窗后还不动，查执行器状态和日志 |
| 规则导入全是 `NO_METADATA` | 还没有完成过范围发现 | 先完成第一次发现 |
| 规则导入报 `ASSET_NOT_FOUND` | 资产没导入，或导错集群目录 | 先导入对应资产 |
| 资产导入报“已存在但不同” | 默认模式不覆盖已有资产 | 确认要改时用 `UPDATE_EXPLICIT` |
| 确认导入时报 `PREVIEW_STALE` | 预览后数据有变化 | 重新预览再确认 |
| 批准时报 `APPROVAL_REF_REQUIRED` | 全局审批依据未登记 | 手工填写“审批依据”，或联系研发检查配置 |
| 规则批准不了 | 规则是 UNSUPPORTED，或状态不是 DRAFT | 查看 support_reason；UNSUPPORTED 的规则需要修改规则或接受不校验 |
| 清单里大量 `TABLE_ABSENT` | 导错集群、库表名不一致 | 核对资产文件与离线包对应的集群 |
| 清单里大量 `UNKNOWN` | 连接失败或超时 | 查看执行器日志，检查网络、账号、SR 状态，修复后重新发现 |
| 清单里 `ACCESS_DENIED` | 只读账号权限不足 | 请 DBA 授权，然后重新发现 |
| `DISCOVERY_RUNNING` | 已有发现在跑 | 等它完成 |
| 计划运行报 `NO_CONFIRMED_MANIFEST` | 还没确认过清单 | 先确认清单 |
| `WINDOW_CLOSED`（延长或关闭窗口时） | 只能在开窗时操作 | 20:00–次日 08:00 内再操作 |
| 大量检查 ERROR，原因为超时 | SR 负载高、并发过高，或表太大 | 查看对应集群和类型池的 P95、超时率与 SR 负载；对大表调低优先级或 PAUSE；必要时降低该类型池并发 |
| 某类型长期 READY 且 ETA 超出窗口 | 该类型并发或单查询吞吐不足 | 查看该池的 live/limit、完成速率和最老队龄；压测后显式调整该集群该类型并发，见 9.6 |
| 新分区没有被校验 | 没有重新发现并确认清单 | 见 7.2 |
| 日报没有生成 | controller 在 08:15 前后不在运行，或处于 RECOVERY | 查看 controller 日志；可以在报告页“重新生成” |

### 13.4 收集信息给研发

```bash
srdq status > /tmp/srdq-status.json
journalctl -u 'srdq-*' --since "-1 day" --no-pager > /tmp/srdq-journal.log
readlink /opt/srdq/current
```

> 不要把 `/etc/srdq/secrets/` 下的文件、离线包或含原值的差异截图发到公开渠道。

## 14. 附录

### 14.1 命令行速查

前提是已经定义 `alias srdq='sudo -u srdq-ctl env SRDQ_CONFIG=/etc/srdq/config.yaml /opt/srdq/current/venv/bin/srdq'`。

| 命令 | 说明 |
|---|---|
| `srdq check-config` | 校验配置和凭证文件权限 |
| `srdq status` | 打印看板摘要 |
| `srdq import assets FILE [--mode UPDATE_EXPLICIT] [--confirm --reason R]` | 导入资产（不加 `--confirm` 时只预览） |
| `srdq import metric FILE [--confirm --reason R]` | 导入 METRIC 规则 |
| `srdq import sample FILE [--confirm --reason R]` | 导入 SAMPLE 规则 |
| `srdq recovery enter --reason R` / `srdq recovery confirm --reason R` | 进入或确认 RECOVERY |
| `srdq report stage --start D --end D --reason R` | 生成阶段报告 |
| `srdq report regenerate-daily YYYY-MM-DD --reason R` | 重新生成日报 |
| `srdq tick` | 手动执行一次调度（排障用） |
| `sudo /opt/srdq/bin/srdq-pg-backup [--label L]` | 手动备份 |
| `sudo /opt/srdq/deploy/upgrade.sh`（在新包解压目录中执行 `deploy/upgrade.sh`） | 升级 |
| `sudo /opt/srdq/deploy/rollback.sh <版本> <dump>` | 回滚或恢复 |

导入用的 CSV 必须能被 `srdq-ctl` 读取，建议先 `install -m 0644 xxx.csv /tmp/`。

| POST | `/manifests/{id}/confirm` 或 `/reject` | 确认或驳回清单 |

| POST | `/check-rules/approve` | `{"rule_ids":[...],"approval_ref":"可选","reason":"..."}` |

### 14.3 状态与术语对照

| 术语 | 含义 |
|---|---|
| 资产（asset） | 一对需要比对的表：华为侧库表 ↔ 阿里侧库表 |
| 规则（check rule） | 对资产做什么检查，有版本，状态为 DRAFT、APPROVED、SUPERSEDED、ARCHIVED |
| 范围清单（manifest） | 一次发现得到的“每张表按哪些分区校验”，状态为 DRAFT、CONFIRMED、REJECTED、SUPERSEDED |
| 范围条目（scope entry） | 清单中的一个分区或整表范围 |
| 校验组（cluster pair） | 固定配对的一个 SOURCE 物理集群和一个 TARGET 物理集群；资产只能属于一个组 |
| 计划（plan） | 校验哪些校验组、资产、档位，以及使用哪版清单 |
| 周期（schedule） | 计划的自动触发方式 |
| 运行（run） | 一次具体执行，创建时冻结规则和清单 |
| 观察（observation） | 一项检查在所属校验组两端各执行一次查询的过程 |
| 比较（comparison） | 组内两端观察结果的比对和结论 |
| 差异链（difference） | 同一检查连续比对的差异历史：NEW、PERSISTENT、RESOLVED |
| 窗口（window） | 每日允许访问 SR 的时间段，20:00–次日 08:00 |
| 类型池（pool） | 每个物理集群独立的 COUNT、METRIC、SAMPLE、METADATA、DEEP 并发池 |
| RECOVERY | 从备份恢复后的保护模式，确认前不派发工作 |

- [ ] 本机 `/tmp` 下的安装包已删除。
