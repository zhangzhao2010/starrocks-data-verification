## 1. 背景

### 1.1 业务背景

- 客户数仓正在从**华为云 StarRocks**迁移到**阿里云 StarRocks**。迁移验收期内，两端同时在线、并行加工写入（双跑）。
- 规模：**数千张表、数十万个分区，单端存储量约 200TB（压缩后）**。见 §2.3。
- 数仓分层：ODS / DWD / DWS / ADS / DIM，另有 OTHER。
- 数据由 Flink、DataX、Hera、DataWorks 等任务加工写入。DataWorks 尚未开通，**拿不到血缘，也拿不到生产任务的运行信息**。
- 两端由现有**专线**互通。

### 1.2 问题

验收期需要一个**持续运行**的校验程序：周期性比对两端 StarRocks 中的数据，发现差异、支持定位并留存证据，为迁移验收提供依据。

### 1.3 设计演进与本期取向

| 版本 | 主要内容 |
|---|---|
| v1.0 | 统一表检查、分片、内容摘要和定位 |
| v1.1 | 双 Worker、本云计算、专线通信 |
| v1.2 | 在线观察；去掉对血缘和生产任务的依赖；优先级、Web 控制、周期；31 张控制表 DDL |
| **v1.3（本期）** | **三档轻量化**：所有表 COUNT 打底，核心表加指标，指定表抽样指纹；默认阿里 ECS 集中执行，华为 Worker 改为可选 |

v1.2 默认对所有表做全字段内容指纹，并在两端各部署一台 Worker，成本和运维负担都偏高。v1.3 把**默认校验深度降为三档、可叠加的检查**，全字段指纹只作为经审批的局部诊断。

## 2. 目标与项目约束

### 2.1 目标

| 编号 | 目标 | 说明 |
|---|---|---|
| G1 | 全范围计数覆盖 | 所有纳入、启用的表，对已确认的每个逻辑分区执行**精确 `COUNT(*)`**；无分区表按整表计数；持续轮巡，历史分区也包括在内 |
| G2 | 核心表指标增强 | 对指定核心表按分区执行 SUM，或按有限维度 GROUP BY 后执行 COUNT/SUM |
| G3 | 内容抽检 | 对指定表做约 0.1% 的**确定性键抽样**，比较样本的键集合和行指纹 |
| G4 | 轻量部署 | 默认只在阿里云部署一台校验 ECS，连接两端 SR；华为侧 Worker 为可选回退 |
| G5 | 可控、可追溯 | 支持优先级、启停、取消、周期调度、局部复查；PostgreSQL 留存计划、规则、运行、结果、差异和审计 |
| G6 | 如实报告 | 按证据类型分别报告"相同 / 不同 / 不可判定 / 未完成"，不夸大结论 |

### 2.2 项目约束（第 1 轮已确认）

| 项 | 结论 | 对设计的影响 |
|---|---|---|
| 工具定位 | 迁移验收期专用，使用 3～6 个月 | 按"可信、够用"的工具建设，不按长期平台建设；验收结束后下线 |
| 时间关系 | 验收期在工具就绪后才开始 | 首期不需要抢先上线部分能力 |
| 交付方式 | 一次性交付，首期 3 个月以上 | 按 P0～P5 推进，P5 的 PoC 通过后才正式用于验收 |
| 研发投入 | 5 人以上 | 可以实现 v1.3 的主体能力 |
| 使用者 | 只有一位使用者（实施负责人本人） | 不做账号、登录、角色和多租户 |
| 运行环境 | 阿里云上的一台 ECS | Web 只监听本机地址，通过 SSH 端口转发访问 |
| 多 owner | 去掉 | 系统只有一个租户，数据模型中不再有 `owner_id` |
| 执行模式 | 首期只做 CENTRAL，LOCAL 留作预案，HYBRID 后置 | 执行器代码与部署位置无关；不实现按资产选择执行池 |
| 预算结算 | 保留原设计 | 保留 RUN/NODE 两级预留、累计用量和超支结算 |

### 2.3 规模与运行窗口（第 2 轮已确认）

| 项 | 结论 | 对设计的影响 |
|---|---|---|
| 数据量 | 单端约 200TB，按压缩后的存储量计 | 原始数据量更大，扫描与样本量按该口径估算 |
| 表与分区 | 数千张表，数十万个分区 | 每侧每轮 COUNT 查询为数十万次 |
| 核心表 | METRIC、SAMPLE 各约数百张表 | 同一张表可以同时配置两类检查 |
| 目标频率 | COUNT、METRIC、SAMPLE 都以**每天覆盖全部分区**为目标，历史分区也包括在内 | 这是目标，不是 SLA，能否达到由 PoC 实测 |
| 跑不完时 | 一轮可以跨多夜续跑 | 报告显示本轮进度和实际轮巡周期，不把未跑到的范围算作完成 |
| 执行窗口 | 只在低峰时段执行，例如每天 0–8 点 | 窗口外不派发任何业务查询 |
| 窗口结束 | 提前停止派发（例如 7:30），到点（8:00）取消仍在执行的查询并确认终止 | 被取消的观察作废，次夜双侧重新读取 |
| 夜间顺序 | 按检查类型分批：先 COUNT，再 METRIC，最后 SAMPLE | 类型内部仍按优先级排序；COUNT 占满窗口时，METRIC 和 SAMPLE 顺延 |
| SR 资源隔离 | 两端都不能为校验账号单独配置资源组，与业务共用资源 | 只能靠工具自身控制并发、超时和熔断 |
| 专线 | 校验可用带宽至少 1Gbps | 样本传输一般不是瓶颈，但仍设置跨云字节预算 |

### 2.4 数据授权与部署（第 3 轮已确认）

| 项 | 结论 | 对设计的影响 |
|---|---|---|
| 样本外传 | 华为侧样本的键和全部约定比较列都可以经专线传到阿里 ECS | CENTRAL 成立，首期不需要华为 Worker |
| 分组值外传 | METRIC 的分组维度值和聚合值都可以外传并保存 | 不需要对小分组单独脱敏 |
| 授权方式 | 全局授权一次：在配置中登记一次客户的审批依据，覆盖 COUNT / METRIC / SAMPLE | 规则不再逐条审批外传类别；撤销全局授权会立即阻断尚未执行的任务 |
| DEEP 明细 | 可以外传，每次发起 DEEP 时确认范围和字节上限 | DEEP 是唯一需要按次确认外传的检查 |
| 原值留存 | 样本原值、分组原值、DEEP 明细保留 7 天，到期自动删除 | 计数、摘要、行指纹、比较结论和差异记录保留到验收期结束；超过 7 天的差异只能通过重读来定位字段 |
| PG 部署 | 与校验程序部署在同一台 ECS 上 | 需要预留资源、使用独立数据盘、每日异机备份，并做恢复演练 |
| 凭证 | 每个 side 一个本机凭证文件，权限 0600，属于该 side 执行器的系统用户 | 不依赖外部秘密管理服务；Controller 和浏览器都读不到 SR 凭证 |

### 2.5 三档检查细节（第 4 轮已确认）

| 项 | 结论 | 对设计的影响 |
|---|---|---|
| SAMPLE 的键 | 大多数抽样表是单列整数主键；首期也支持**单列字符串键** | 两种键契约都要做 S1 下推适配和双端向量测试；复合键推迟 |
| 唯一性依据 | 只认表模型：Primary / Unique 模型的完整单列键 | Duplicate、Aggregate 表不做 SAMPLE，只做 COUNT 和 METRIC；不接受外部提供的唯一性证明 |
| METRIC 规则来源 | 业务方逐表给出指标（列、函数、维度、过滤、精度） | 工具不推断指标；规则质量和交付时间取决于业务方 |
| SAMPLE 比较列 | 业务方逐表指定 | 未指定的列不进入指纹，报告中要写明比较的列范围 |
| 输入方式 | 业务方用 Excel 模板填写，导出为 UTF-8 CSV 后上传 | 规则走"预览 → 确认"，并对照两端元数据逐行校验 |
| 浮点列 | 目前不清楚有没有、有多少 | 保持 REQUIRE_POLICY：模板中有容差列；浮点列没有填容差时，该规则为 UNSUPPORTED，并在预览时标出 |

### 2.6 差异处理（第 5 轮已确认）

| 项 | 结论 | 对设计的影响 |
|---|---|---|
| 上报方式 | 观察到差异就直接上报，不自动复核 | 一部分差异可能只是在线写入的时差，报告中必须写明；靠"持续情况"区分偶发和持续 |
| 持续情况 | 根据历次结果自动标出 NEW（新出现）/ PERSISTENT（持续，带连续次数）/ RESOLVED（已消失） | 不增加查询，只汇总已有结果 |
| 分诊记录 | 工具里不记录差异的解释和处理结论 | 差异清单没有处理状态；解释、修复在线下完成 |
| DEEP 发起 | 只由使用者手工发起 | 工具不自动执行，也不给候选列表 |
| 疑似存储损坏 | 查询返回 tablet / 副本 / 校验类错误时记为 ERROR，单列报告，由使用者转运维线下处理 | 不自动暂停表，按普通错误退避重试 |
| 通知 | 只看看板，外加每天窗口结束后生成的日报文件 | 不对外发送消息，ECS 不需要外网出口 |
| 日报内容 | 当夜进度与轮巡周期、差异清单、未完成与不支持项、负载与熔断记录 | 见 FR-15 |
| 报告格式 | Excel 可打开的 CSV 明细 + Markdown 正文（需要时转 PDF） | 首期不生成 xlsx，不内置 PDF 渲染 |

### 2.7 技术选型与简化（第 6 轮已确认）

| 项 | 结论 | 对设计的影响 |
|---|---|---|
| 语言 | Python | Controller、执行器、Web 用同一种语言，编码协议只实现一份 |
| Web | 服务端渲染的简单页面（FastAPI + Jinja2） | 不做前后端分离，不需要前端构建 |
| 数据访问 | psycopg3 手写 SQL，不用 ORM | 事务和锁的写法显式可查 |
| 控制库 | 全新 schema，不兼容 v1.2 | 不迁移 v1.2 的数据；控制表由 35 张精简为 32 张 |
| 表合并 | 应验项、覆盖汇总并入 run_check；导入行并入导入批次 | 分母仍不可变，由数据库约束保证 |
| 留存材料诊断 | 去掉 CAPTURED_MATERIAL | DEEP 一律双侧重读，占用窗口内的查询 |

### 2.8 SR 兼容性与 PoC（第 7 轮已确认）

| 项 | 结论 | 对设计的影响 |
|---|---|---|
| SR 版本 | 两端同为 StarRocks 3.x | 仍要逐项探测函数、取消和会话变量；版本记录精确到补丁版本，任一端升级后重新探测 |
| TLS | 两端都支持可校验的 TLS | 按设计强制 TLS 和证书校验，没有例外 |
| PoC 环境 | 直接在生产两端的执行窗口内做 | 从低并发起步；已知真值用例放在 DBA 建的隔离库中；不改真实数据，不动专线 |
| 熔断阈值 | PoC 实测后与 DBA 商定 | 配置中先放保守初值，PoC 结束时定稿 |
| SR 负载信号 | 只能用只读账号查系统视图 | 不访问 metrics 端口；查不到的信号不启用，退回只看校验查询自身的指标 |
| 存储错误识别 | 关键字初始列表，PoC 中补充 | tablet、replica、checksum、corrupt 等；修订写审计 |
| PoC 门槛 | S1 采样两端一致、COUNT 全量 ≤ 1 夜、对业务影响可接受、取消与恢复可靠 | 四项全部通过才用于验收；见 §10 |

## 3. 范围与非目标

### 3.1 本期范围

- 表存在性、逻辑结构、分区范围的并集，以及缺失和未知项的识别。
- 三类检查：COUNT（基线）、METRIC（可选）、SAMPLE（可选），外加经审批的 DEEP 局部诊断。
- 范围级（表 / 分区 / 分片）和规则级的任务控制。
- 周期调度：CRON、固定间隔、完成后连续轮巡。
- 轻量 Web 控制台和 API。
- PostgreSQL 控制库：计划、规则、运行、尝试、原始结果、比较、分母、审计。

### 3.2 非目标（明确不承诺）

1. **不**采集或推断 Flink / DataX / Hera / DataWorks 的任务成功率、漏跑或端到端延迟。
2. **不**知道源端 MySQL 的业务真值：两端相同不代表业务正确。
3. **不**保证两端读到的是同一时刻的数据（共同快照）。同时发起查询、多轮结果相同，都不能证明这一点。
4. **不**证明全表逐行内容一致：COUNT、SUM、样本指纹相同都不等于全量逐行相同。
5. **不**做物理副本或文件健康检测：COUNT 可能只读部分列，抽样也不覆盖全部数据页。
6. **不**自动修复数据、重跑生产 SQL、停写、切流，也不删除历史证据。
7. 本期**不**引入 DataWorks、Kubernetes 或消息队列。
8. **不**做多租户、账号体系、登录、SSO 和角色权限。
9. 首期**不**做 HYBRID（按资产选择执行位置）；LOCAL 只作为预案，需要时再部署。
10. **不**在工具里记录差异的分诊和处理结论，也**不**向外发送通知（钉钉、企业微信、邮件、webhook）。

## 4. 干系人与系统角色

### 4.1 干系人

| 角色 | 需要准备 | 产出 |
|---|---|---|
| 客户数据负责人 | 表名单、指标与抽样规则、列口径和例外 | 批准范围和规则，解释差异 |
| 平台 / 安全 / 运维 | 版本信息、只读账号、TLS、专线白名单、负载基线 | 访问和数据外传授权，资源与恢复预算 |
| 实施与校验团队 | 适配三类检查和结果协议，执行 PoC | 兼容性、扫描与传输、控制与恢复的证据 |

### 4.2 工具使用者

- 只有一位使用者，即实施负责人本人。工具里不区分角色，所有操作都由这位使用者完成。
- 客户方的审批（例如数据外传、局部深查、范围排除）在线下完成。使用者在工具里**确认**时，登记审批依据（审批人、审批单号或说明），并写入审计。
- 保留"预览 → 确认"这道流程，用于防止误操作，而不是用于权限控制。

## 5. 术语

| 术语 | 含义 |
|---|---|
| 对照端 / source | 华为云 StarRocks |
| 目标端 / target | 阿里云 StarRocks |
| side | 逻辑侧：`huawei` 或 `aliyun`，表示"读哪一端的数据" |
| execution_location | 执行进程的物理位置（ALIYUN / HUAWEI），与 side 相互独立 |
| 资产 asset | 一组表映射（source 库表 → target 库表），带层级、优先级、启用标志 |
| 规则 check_rule | 资产上的一条检查定义，有稳定 `rule_key` 和不可变的批准版本 |
| 范围清单 manifest | 经确认的逻辑分区范围集合，取两端并集 |
| 运行 run | 一轮校验。创建时冻结规则版本、范围和分母 |
| run_check | 运行中"某个范围 × 某条规则"的执行单元 |
| expected | 应验项，即分母中的一项（范围 × 规则） |
| 观察 observation | 某个 run_check 的一次双侧配对读取 |
| 证据 evidence | 实际取得的证据类型：COUNT / METRIC / SAMPLE / CONTENT_HASH / EXACT |
| coverage | 每个 expected 的当前完成和相同情况汇总 |

## 6. 功能需求

### FR-01 资产导入

- 兼容 v1.2 的**七列 CSV**：`layer,source_db,source_table,target_db,target_table,priority,enabled`。也接受等价的 JSON `asset-list-v1`。
- 编码 UTF-8，可带 BOM，按 RFC4180 解析。可以单文件导入，也可以按层拆成多个文件；`layer` 每行必填，与文件名冲突时报错。
- 字段规则：
  - `layer` 取值 ODS / DWD / DWS / ADS / DIM / OTHER。
  - source 库表必填，target 默认与 source 同名。
  - `priority` 为 0～100 的整数，默认 50。
  - `enabled` 只接受 `true` / `false`，默认 `true`。
- CSV 中**不允许**填写地址、密码或 DSN。数据源对在页面上从已注册对象中选择。
- 导入流程：
  1. **预览**：逐行列出新增、重复、错误、冲突、越权项。确认之前不修改资产。
  2. **确认**：校验文件摘要、预览结果和资产版本，整批原子生效。
- 默认模式 `CREATE_OR_VALIDATE` 不会隐式覆盖已有映射或优先级。需要更新时用 `UPDATE_EXPLICIT`，并提供 `update_fields` 和 `expected_revision`。
- 新名单中没有出现的旧资产**不会**被自动归档。标识符不统一转小写。
- 导出 CSV 时防范公式注入；上传有格式、编码、行数和字节限制。

**验收**：CSV 与 JSON 导入后得到同一个模型；行级错误可以定位；省略字段不会覆盖人工设置的值。

### FR-02 范围发现与确认

- 两个逻辑执行器分别采集两端的表、结构和分区元数据，与已登记的历史范围合并，生成**并集**清单。
- 预览中需显示：包含、单侧缺失、未知、NULL 范围、范围外、审批排除项，并附原因。
- 分区按**逻辑语义**配对：
  - range 分区按同一字段、同一类型的半开区间配对。
  - list 分区按规范化后的值集合配对。
  - 无分区表使用 `ALL`。
  - **不**按物理 PartitionId / TabletId 配对，**不**根据 `dt`、`updated_at` 之类的列名推断时间范围。
- 元数据状态需细分为：PRESENT、ABSENT_CONFIRMED、ACCESS_DENIED、UNKNOWN、QUERY_FAILED。空列表不等于缺表，也不等于 0 行。
- 清单生命周期为 DRAFT → CONFIRMED → SUPERSEDED。确认后不可原地修改；新范围产生新版本。
- 新分区默认 `REQUIRE_CONFIRM`，可批准为 `AUTO_ADD_COMPATIBLE`。消失的分区保留缺失记录，**不减少分母**。
- 存在未知项时 `inventory_complete=false`，只显示"已知范围完成率 + 未知阻断数"。

**验收**：缺表、无权限、未知项不会被当作 0 行，也不会从分母中消失。

### FR-03 COUNT 基线检查

- 资产首次确认时，自动生成保留规则 `rule_key=baseline_count`。
- 对每个范围执行精确 `COUNT(*)`，不加业务过滤。不能用 `COUNT(column)` 或元数据 RowCount 代替。
- 比较精确整数，并记录有符号差和绝对差；不使用默认的 1% 容差。source 为 0 时相对差为 NULL。
- 禁用基线必须显式登记为排除或暂停并留审计，不能静默移出"全部表 COUNT"的目标。

### FR-04 METRIC 指标检查

- 规则用结构化 JSON 定义，至少包括：分组维度 `group_by`、结构化过滤、度量列表（COUNT_ROWS / COUNT_NONNULL / SUM）、精度、容差、最大分组数、最大键长、最大结果字节。
- 一条规则只能有一组 `group_by` 和一个过滤条件；需要多种维度时拆成多条规则。
- 每个分组强制返回组行数；每个 SUM 字段自动附带非空计数，用来区分 NULL 和 0。
- 聚合在 StarRocks 端完成，不允许把明细拉回 ECS 再聚合。
- 比较分组键的并集：单侧缺组属于差异。整数和 DECIMAL 精确比较；浮点必须显式配置容差，否则标为 UNSUPPORTED。
- 不接受原始 SQL、原始 WHERE、任意函数或表达式脚本。表、列、函数都来自批准的白名单，值用参数绑定。
- 规则由业务方逐表给出，通过 `metric_rules.csv` 模板导入（一行一个指标，同一 `rule_key` 的多行合成一条规则）。见 [03-技术设计 §4.6](03-技术设计.md#46-规则模板csv第-4-轮)。

**验收**：模板中的错误（表不在名单中、列不存在、类型不兼容、同一规则的维度或过滤不一致）在预览中逐行定位；浮点列没有容差时显示 UNSUPPORTED，且该规则仍计入分母。

### FR-05 SAMPLE 抽样指纹检查

- 抽样比例约 1/1000，由 `bucket_count=1000, selected_bucket=0` 派生，首期固定这两个值。
- 两端在各自的相同逻辑范围上**独立**执行同一个确定性键谓词：`SHA-256(固定种子 + 规范化完整键) mod 1000 == 0`。这样单侧多出或缺少的键也能被抽中。
- 样本筛选必须**在 StarRocks 端下推**执行。不支持下推时标为 UNSUPPORTED，**禁止**退化为全量拉取后在客户端抽样。
- 首期支持**单列、非空、唯一的整数键或字符串键**，唯一性只认表模型（Primary / Unique 的完整单列键）。Duplicate、Aggregate 表和其他无可靠唯一键的表，SAMPLE 标为不适用，COUNT 和 METRIC 照常执行。
- 字符串键按原始 UTF-8 字节编码，不 trim、不改大小写；两端对 CHAR 尾部空格等语义不一致时标为 UNSUPPORTED。
- 键列和比较列由业务方通过 `sample_rules.csv` 模板逐表指定；种子使用项目统一的默认值，并写入每个规则版本。
- 执行器对样本做规范化编码，计算行指纹，比较键集合和指纹。
- 两侧样本都为空时结论为 INCONCLUSIVE（样本不足），不算通过。
- 种子、键列、编码、比例写入规则版本；任何变更都产生新版本。

### FR-06 DEEP 局部诊断

- 可以从 COUNT 差异、METRIC 差异组、SAMPLE 差异发起"局部复查"，也可以手工指定表、分区或共同键范围。**只能由使用者手工发起**，工具不自动执行，也不生成候选列表。
- 默认沿用原检查类型复查，**不自动升级到全表**。
- 全字段指纹（CONTENT_HASH）或精确比对（EXACT）必须显式指定 `check_kind=DEEP`，并具备批准的范围、预算和明细授权。
- 数据来源只有 `LIVE_REREAD`：双侧重新读取。不使用已留存的样本或分组材料做诊断（第 6 轮）。
- 差异定位：有键时按键和行哈希定位到字段；无键时按完整行及出现次数比对。UI 最多展示 100 条，总数未完整枚举时标 AT_LEAST 或 UNKNOWN。

### FR-07 计划与周期

- 计划引用一个已确认的清单，以及允许的规则选择器 `check_selector`（kinds / rule_keys）。
- 周期类型：
  - `CRON`：带 IANA 时区，预览未来 5 次触发时间。
  - `INTERVAL`：间隔不少于 60 秒，锚定起点，不随轮询漂移。
  - `CONTINUOUS`：本轮正常完成后休息 `rest_seconds`（不少于 60 秒）再启动下一轮。
- 不同检查类型可以配置不同频率。首期目标是三类检查都每天覆盖全部分区；推荐每类各配一个 `CONTINUOUS` 周期，跑完一轮马上开始下一轮。
- 重叠策略为 SKIP 或 COALESCE（最多一个待执行）；错过触发时为 SKIP 或 LATEST，不无限补历史轮次。
- 同一次触发最多产生一个 run。
- **执行窗口**：
  - 业务查询只在配置的窗口内派发，例如每天 0–8 点。窗口是全局的派发门控，与周期触发是两回事。
  - 一个 run 在窗口外保持未完成，下一个窗口开始时从未完成的范围接着跑，已完成的范围不重跑。
  - 到停派时刻（例如 7:30）不再开始新观察；到截止时刻（例如 8:00）取消所有在途查询，并确认两端已终止。
  - 被取消的观察不发布结论，对应范围在下一个窗口用新观察双侧重读。
  - 报告显示每一轮的开始时间、已跑的窗口数和实际轮巡周期。

### FR-08 调度优先级

- 排序规则：`检查类型(COUNT<METRIC<SAMPLE) → priority DESC → 层级(ODS<DWD<DWS<ADS<DIM<OTHER) → 就绪顺序 FIFO`。
  - 检查类型分批是第 2 轮确认的：只要还有可派的 COUNT，就不派 METRIC 或 SAMPLE。
  - 分批不是硬屏障：COUNT 因资产槽或并发而派不出去时，空出来的并发可以给其他类型使用，不让 SR 空闲。
- **没有跨表血缘屏障**：例如优先级 90 的 DWD 表先于优先级 50 的 ODS 表执行。
- 优先级覆盖按以下顺序继承：run_check > 叶节点 > 最近祖先 > 范围策略 > 资产默认。
- 修改优先级不抢占正在执行的查询，也不使已有结果失效。

### FR-09 任务控制

| 操作 | 要求 |
|---|---|
| START / RESUME | 前提满足后进入 READY；已完成项不重跑 |
| PAUSE | 不再开启新观察；已开始的双侧观察排空 |
| CANCEL | 请求终止两端 SQL；确认停止前显示"取消中" |
| ARCHIVE | 逻辑隐藏，不删除 SR 数据或证据，不减少旧分母 |
| RESTORE | 恢复后默认处于暂停状态，不复活旧的尝试 |
| SET / CLEAR_PRIORITY | 设置或清除显式优先级 |
| REGENERATE | 生成新的 run 或观察，保留旧证据 |

- 控制粒度有两层：范围节点（表 / 分区 / 分片）和规则级（run_check）。子级不能解除父级的暂停。
- 生效范围：`CURRENT_ONLY` 只作用于本轮；`THIS_AND_FUTURE` 同时修改持久策略，对后续新的规则版本也生效。
- 所有操作先 PREVIEW 再 APPLY，需要幂等键、版本号（If-Match）和原因。批量操作中任意一项越权，整体拒绝。

### FR-10 结果比对与差异

- 每个观察只配对同一观察、同一成员、同一规则版本的双侧结果，**不**取"最新两条"。
- 任何一侧需要重读时，双侧都要重新采集（新观察），不把一侧的旧结果与另一侧的新结果拼接比较。
- 差异类型包括：COUNT_DELTA、GROUP_SOURCE_ONLY / TARGET_ONLY、METRIC_VALUE_DIFF / GUARD_DIFF、SAMPLE_KEY_SOURCE_ONLY / TARGET_ONLY、SAMPLE_FIELD_DIFF 等。
- 结果不完整（中断、超限、隐藏截断、解码失败）时不得发布"相同"结论，也不得伪造 0 行结果。
- 差异直接上报，不自动复核。每个"范围 × 规则"按历次完整结论自动标出 NEW / PERSISTENT / RESOLVED，并显示首次发现时间、最近一次结果时间和连续不同的次数。不完整的结果（ERROR、INCONCLUSIVE 等）不计数，也不打断连续次数；规则版本变化后重新计数。
- 查询返回疑似存储损坏的错误（tablet / 副本不可用、数据校验失败等）时，记为 ERROR 并归类为 STORAGE_SUSPECT，在看板和日报中单列；按普通错误退避重试，不自动暂停表。

**验收**：EQUAL → DIFFERENT → DIFFERENT → EQUAL 依次显示为 NEW、PERSISTENT（2 次）、RESOLVED；STORAGE_SUSPECT 单列且不被当作差异或相同。

### FR-11 覆盖看板

按检查类型**分别**统计，不得混用：

- **COUNT**：应验范围数、完成数、相同数、差异数、失败或未知数、最久未验证的时长。
- **METRIC**：规则和指标数、应验范围、完整返回的组数、缺组或度量差异、超预算和不支持项。
- **SAMPLE**：应验范围、实际样本数、参考入样比例、样本键或指纹差异、样本不足和不支持项。

口径：

- 完成率 = 已完成 expected / 应验 expected。
- 观察相同覆盖率 = 相同 expected / 应验 expected。
- 有完整结论的差异计入"完成"，但不计入"相同"。失败、空样本、不支持都不算完成。

示例：100 个 COUNT 应验项中，90 个相同、5 个差异、5 个失败，则完成率 95%，观察相同覆盖率 90%。

### FR-12 执行器管理

- 展示逻辑 side 与物理位置（两者分开显示），以及心跳、租约、在途查询、磁盘、待发箱、备份状态。
- 执行器按 side 隔离，不能领取另一侧的任务，也不能读取另一侧的数据源。

### FR-13 规则版本与确认

> "批准"指使用者在工具中确认规则，并登记线下审批依据，见 §4.2。

- `rule_key` 在资产内保持稳定，每个版本有独立 ID。版本状态为 DRAFT → APPROVED → SUPERSEDED / ARCHIVED。
- 已批准的定义不可修改。修改列、维度、过滤、容差、种子、比例、预算、执行位置或传输类别时，都会生成新版本。
- 已经开始的 run 继续使用冻结的旧版本。权限一旦撤销，立即阻断尚未执行的任务。
- 规则模板导入是幂等的：重复导入相同内容不生成新版本；某行定义变化时只为对应规则生成新版本。批准可以按导入批次一次完成。

### FR-14 审计

记录以下内容：操作时间、对象、版本、所依据的线下审批、变更前后的内容和冲突情况，以及操作原因（必填）。由于只有一位使用者，操作者固定为本地使用者。审计记录只追加，不修改历史。

### FR-15 日报与阶段报告

- 每天窗口结束、所有在途查询确认终止后，自动生成一份日报；超过宽限时间（默认 15 分钟）仍有未确认的取消时照常生成，并列出这些查询。
- 日报包含四部分：
  1. 进度与轮巡周期：每类检查的当夜完成数、本轮累计进度、已用窗口数、预计还需几夜、最久未验证的范围。
  2. 差异清单：按检查类型、层级、表列出 NEW / PERSISTENT / RESOLVED。
  3. 未完成与不支持项：失败（单列疑似存储错误）、超预算、不支持、样本不足、阻断、作废，以及原因。
  4. 负载与熔断记录：降并发、恢复、熔断、截止取消的次数，以及查询耗时分布。
- 格式：Markdown 正文加 CSV 明细（UTF-8 带 BOM，Excel 可以直接打开）。需要 PDF 时，在本机由 Markdown 转换。
- 使用者可以选定日期区间生成阶段报告，格式相同，作为给客户的阶段性材料。
- 报告遵守 §9 的用语规范，并固定声明："共同快照保证：无"，以及"差异可能来自在线写入时差"。
- 报告文件保存在本机，保留到验收期结束；不对外发送。

**验收**：同一窗口只生成一份日报；四部分都有；CSV 能用 Excel 正确打开且防公式注入；报告不包含已过期的原值。

## 7. 非功能需求

### 7.1 性能与容量

- 目标是三类检查每天覆盖全部分区（§2.3）。所有业务查询都要在执行窗口内完成，到截止时刻前确认终止。
- 任务数量按"分区数 × 规则数"计算，不按表数估算。粗算：30 万分区、7.5 小时有效窗口时，每侧仅 COUNT 就需要约 11 条/秒；在并发 8 时，每条平均需在 0.7 秒内完成。达不到时，一轮跨多夜完成。
- PoC 必须实测并给出以下数据：COUNT、METRIC、SAMPLE 每 TB 的耗时；一轮全量所需的窗口数；对业务查询延迟的影响。
- 抽样的预期返回量：1000 万行分区约 1 万行、约 10MB；10 亿行约 1GB。按每行 1000 字节估算，十进制单位，不含协议开销和重试。

### 7.2 资源保护

- 以下几项分别设置预算：SR 查询并发、扫描时长、结果字节、分组数、样本数、跨云字节、ECS 内存和临时磁盘。
- SR 没有专用资源组，与业务共用资源。工具必须自己控制每个集群的并发和单条查询超时，并在可行时设置会话级的内存上限。
- 观测到 SR 负载异常时（例如查询明显变慢、错误率上升）自动降低并发或暂停派发；使用者可以随时一键暂停全部派发。
- 超出预算时标为未完成并取消查询，**不得截断结果后判定相同**。
- 达到业务阈值时停止接收重任务，但心跳、取消和告警保持可用。

### 7.3 安全

- SR 连接只用只读账号；连接 SR 必须使用经过校验的 TLS（证书链、主机名、有效期）。专线不能替代加密，不得回退到公网，不得关闭证书校验。
- 两端凭证都保存在这台 ECS 上，按进程隔离：每个 side 的执行器以独立的系统用户运行，只能读自己的凭证文件（权限 0600）。界面和配置中只用 `connection_ref` 引用凭证，日志中不出现明文。
- 数据外传分四级：SUMMARY_ONLY / AGGREGATES_APPROVED / SAMPLE_VALUES_APPROVED / DETAIL_APPROVED。前三级由一次全局授权覆盖；DETAIL_APPROVED 只用于 DEEP，每次确认。
- 样本原值、分组原值、DEEP 明细只保留 7 天，到期自动删除并写审计；PG 备份的保留期同样不超过这个期限加一个备份周期。
- Web 和 API 只监听 `127.0.0.1`，通过 SSH 端口转发访问；不对内网或公网开放，也没有登录。
  - 浏览器发起的写请求校验 Origin / Host，防止其他网页借本机端口发起请求。
  - 输出转义，CSV 防公式注入。
  - 执行器使用独立的本机接口凭证，不能与浏览器共用同一个入口。
- 只使用参数化的只读 SQL 模板；不接受任意 SQL、DSN、脚本或外部 URL。
- PG 不对公网开放；执行器不能直接写 PG；校验主机不与 SR 的 FE / BE 混部。

### 7.4 可靠性与恢复

- 执行器使用租约（PoC 初值：租约 120 秒，心跳 30 秒）。查询取消必须经过确认；在确认之前保持 CANCEL_PENDING，并持续占用资产槽。
- 执行器本地有待发箱，用于在重启或断网后对账结果。
- PG 与校验程序同机，使用独立数据盘；每日备份到异地（例如 OSS），并做恢复演练。从旧备份恢复后，生成新的控制代号，旧的未接受结果一律不采用，丢失的时间段标为 UNKNOWN。
- 首期接受一台 ECS 同时影响两侧的故障域，**不宣称高可用**。

### 7.5 可观测性

监控以下指标：扫描量、SR CPU / IO / 业务延迟、返回字节、样本数和分组数、内存和外排、PG 事务、队列等待时长。

### 7.6 兼容性

- v1.3 使用全新的控制库 schema，不读取、不迁移 v1.2 的配置、结果和 DDL；v1.2 与 v1.3 的协议不能混用，收到 v1.2 格式的消息一律拒绝。
- 七列 CSV 格式保持兼容。

## 8. 约束与假设

- 程序只依赖 SR 中的数据和元信息，默认 `read_mode=ONLINE_ONLY`、`temporal_assurance=NONE`。
- 两端 SR 版本需要支持同语义的服务端过滤（内置的 SHA-256、hex、精确取模组合），并通过兼容性测试。
- 专线能访问华为 SR 的只读私网端点。
- 客户已同意样本字段和分组值进入阿里 ECS（第 3 轮），因此首期采用 CENTRAL。LOCAL 只在授权变化或 PoC 不通过时启用。

## 9. 报告用语规范

| 允许使用 | 禁止使用 |
|---|---|
| 本轮数量相同 / 指标相同 / 样本相同 | 迁移验收通过 |
| 观察到差异 | 全量内容一致 |
| 不可判定 / 样本不足 / 未完成 / 不支持 | 同一时刻三项一致 |
| 共同快照保证：无 | 100% 行已比较（指抽样） |

报告中必须同时显示：证据类型、比较的列范围、双端读取的时间区间、规则版本。

## 10. 验收标准

按以下层次逐层验收，前一层通过不能代替后一层：

1. 协议本地参考向量（C1 / S1 / D1）。
2. 隔离环境中的 v1.3 DDL 和约束。
3. 服务并发与状态机。
4. 真实 SR 上的过滤与查询。
5. 网络与恢复。
6. Web。

COUNT、METRIC、SAMPLE 分别验收各自的证据边界。详细测试清单（V01～V95）见 [03-技术设计 §17](03-技术设计.md#17-测试设计)。

PoC 在生产两端的执行窗口内进行，选取 10～20 张代表表，覆盖：大分区和小分区、宽表、各种表模型、有键和无键、核心指标、历史回刷。以下四项全部通过才正式用于验收（第 7 轮）：

| 门槛 | 通过条件 |
|---|---|
| S1 采样两端一致 | 数据一致的范围内，两端服务端选中的键集合完全相同；整数键和字符串键都覆盖 |
| COUNT 全量 ≤ 1 夜 | 按实测吞吐推算，COUNT 一轮全量不超过 1 个窗口 |
| 对业务影响可接受 | DBA 书面确认窗口内业务查询延迟的变化可以接受 |
| 取消与恢复可靠 | 截止取消、手工取消、进程重启、本机断网后，两端 SQL 都确认终止，结果不重不漏 |

METRIC 和 SAMPLE 的轮巡夜数只实测、如实报告，不设门槛。
