# v1.3 到 v1.4 升级部署手册

本文用于将已安装的单组双集群 v1.3 升级为三组、六个物理集群的 v1.4。流程从交付方准备生产配置并构建离线包开始，到生产升级、验收和回退结束。

> 本文中的离线包包含生产 StarRocks 凭证，必须按敏感制品管理，不得提交 Git、上传普通制品库或通过未经批准的渠道传输。

## 0. 当前上线门禁

截至 2026-10-12，当前工作树**不能直接用于生产升级**。以下门禁全部关闭并完成预生产演练后，才能执行第 8 章：

- [ ] 正式版本号为 `1.4.0`；生产当前版本不能与新版本相同。
- [ ] 升级脚本会在签发六个 worker token 前，把六个物理集群和三个校验组同步到控制库。
- [ ] 已明确旧资产迁移规则。当前 `0002_multi_cluster.sql` 把 v1.3 资产放入 `legacy`，而生产配置只有 `pair-1`、`pair-2`、`pair-3`，必须先将每个旧资产映射到真实校验组。
- [ ] 升级脚本会停止并处理 v1.3 的 `srdq-executor@huawei.service`、`srdq-executor@aliyun.service`，不能只管理六个 v1.4 实例。
- [ ] 旧版本配置快照只有两份集群凭证时，自动恢复和 `rollback.sh` 仍可恢复旧版本。
- [ ] 已在与生产同版本的操作系统、Python 和 PostgreSQL 数据副本上完成升级及回退演练。

门禁未全部关闭时，只能准备配置和测试包，不得在生产机运行 `upgrade.sh`。

## 1. 角色和目录

| 角色 | 工作目录 | 职责 |
|---|---|---|
| 交付方 | 源码仓库、`/secure/srdq-prod` | 准备配置和凭证、构建并校验离线包 |
| 生产运维 | `/tmp`、`/opt/srdq`、`/etc/srdq`、`/var/lib/srdq` | 校验制品、执行升级、验收或回退 |

生产固定目录：

- 程序：`/opt/srdq/releases/<版本>`，当前版本软链接为 `/opt/srdq/current`。
- 配置：`/etc/srdq/config.yaml`。
- 凭证：`/etc/srdq/secrets/`。
- 数据：`/var/lib/srdq/`。
- 备份：`/var/lib/srdq/backups/`。

## 2. 交付方准备生产配置

### 步骤 1：确定新版本号

新版本号必须不同于生产当前版本，并按发布规则递增。当前源码中的版本位于 `pyproject.toml`：

```toml
[project]
version = "<新版本>"
```

更新版本和锁文件后，先完成全量测试。不要通过改压缩包文件名伪造新版本；安装脚本读取的是包内 `bundle.env`。

### 步骤 2：创建受控 provision 目录

```bash
sudo install -d -m 0700 -o "$USER" -g "$(id -gn)" /secure/srdq-prod
install -d -m 0700 /secure/srdq-prod/secrets
install -m 0600 deploy/config.example.yaml /secure/srdq-prod/config.yaml
```

目录中不得出现符号链接。最终结构必须类似：

```text
/secure/srdq-prod/
├── config.yaml
└── secrets/
    ├── huawei-1.json
    ├── aliyun-1.json
    ├── huawei-2.json
    ├── aliyun-2.json
    ├── huawei-3.json
    ├── aliyun-3.json
    └── sr-ca.pem                 # 使用私有 CA 时才需要
```

`pg.json` 不需要提供，安装程序会在生产机生成本地 PostgreSQL 连接凭证。

### 步骤 3：填写 `config.yaml`

至少确认以下内容：

1. `spec_version` 为 `srdq-config-v1.4`。
2. 正式打包时 `run_enabled: true`。
3. `transfer.global_approval_ref` 填真实书面审批编号，不能保留占位符。
4. 六个 `physical_clusters` 的 ID、凭证路径和操作系统用户严格如下。
5. 三个 `cluster_pairs` 固定一一对应，禁止跨组配对。
6. 根据压测结果填写每个集群的五类并发。
7. 核对执行窗口、Web 监听地址、报告目录和 Controller 地址。

固定映射：

| cluster_id | os_user | credential_file | 校验组 |
|---|---|---|---|
| `huawei-1` | `srdq-hw1` | `/etc/srdq/secrets/huawei-1.json` | `pair-1` SOURCE |
| `aliyun-1` | `srdq-al1` | `/etc/srdq/secrets/aliyun-1.json` | `pair-1` TARGET |
| `huawei-2` | `srdq-hw2` | `/etc/srdq/secrets/huawei-2.json` | `pair-2` SOURCE |
| `aliyun-2` | `srdq-al2` | `/etc/srdq/secrets/aliyun-2.json` | `pair-2` TARGET |
| `huawei-3` | `srdq-hw3` | `/etc/srdq/secrets/huawei-3.json` | `pair-3` SOURCE |
| `aliyun-3` | `srdq-al3` | `/etc/srdq/secrets/aliyun-3.json` | `pair-3` TARGET |

并发配置示例：

```yaml
concurrency: {COUNT: 40, METRIC: 20, SAMPLE: 10, METADATA: 2, DEEP: 2}
```

五类并发相互独立，没有集群总并发上限，也不会跨池借用空闲并发。正式值必须来自真实压测，不能直接把示例值视为生产结论。

### 步骤 4：准备六份 StarRocks 凭证

每个文件至少包含：

```json
{
  "host": "<StarRocks FE 地址>",
  "port": 9030,
  "user": "<只读账号>",
  "password": "<密码>",
  "ssl_ca": "/etc/srdq/secrets/sr-ca.pem"
}
```

要求：

- 六个账号分别限制为对应集群所需的最小只读权限。
- 默认启用 TLS。使用 `ssl_ca` 时，路径必须位于 `/etc/srdq/secrets/`，并把同名 CA 文件放入 provision 的 `secrets/`。
- 凭证中不得填写 `worker_token`；安装或升级脚本负责生成或保留。
- 不得使用 `<...>` 占位值。

设置权限：

```bash
chmod 0600 /secure/srdq-prod/config.yaml
chmod 0600 /secure/srdq-prod/secrets/*
find /secure/srdq-prod -type l -print
```

最后一条命令必须无输出。

## 3. 构建离线包

### 步骤 5：检查构建机

构建机要求：

- x86_64。
- 可用的 `python3`、`pip`、`uv`、`unzip`。
- 构建时能取得锁定依赖对应的 Linux CPython 3.11 wheel；生产机安装过程不访问互联网。

检查：

```bash
uname -m
python3 --version
uv --version
unzip -v >/dev/null
```

### 步骤 6：运行打包脚本

在仓库根目录执行：

```bash
./scripts/build-offline-bundle.sh \
  --provision-dir /secure/srdq-prod
```

脚本会验证配置、六个集群、固定凭证路径、操作系统用户、审批编号和凭证字段。输出：

```text
dist/srdq-offline-<版本>-alinux4-x86_64.tar.gz
dist/srdq-offline-<版本>-alinux4-x86_64.tar.gz.sha256
```

指定其他输出目录时使用：

```bash
./scripts/build-offline-bundle.sh \
  --provision-dir /secure/srdq-prod \
  --out-dir /secure/srdq-release
```

### 步骤 7：在交付前校验制品

```bash
cd dist
sha256sum -c srdq-offline-<版本>-alinux4-x86_64.tar.gz.sha256
stat -c '%a %n' srdq-offline-<版本>-alinux4-x86_64.tar.gz*
tar tzf srdq-offline-<版本>-alinux4-x86_64.tar.gz | less
```

验收标准：

- checksum 输出 `OK`。
- 压缩包和 `.sha256` 权限为 `600`。
- 包内存在 `bundle.env`、`SHA256SUMS`、`wheels/`、`postgresql/`、`deploy/` 和 `provision/`。
- 不解压展示或记录凭证内容。

通过批准的安全介质或加密通道交付两个文件，并通过独立渠道确认 SHA-256。交付完成后按安全制度清理临时副本。

## 4. 生产升级前检查

以下步骤必须由生产运维在关闭窗口内执行，建议安排在 09:00–19:00。

### 步骤 8：接收并校验离线包

把两个文件放到生产机 `/tmp`，然后执行：

```bash
cd /tmp
export VERSION=<新版本>
sha256sum -c "srdq-offline-${VERSION}-alinux4-x86_64.tar.gz.sha256"
```

checksum 不通过时立即停止，不得解压或部署。

### 步骤 9：记录升级前状态

```bash
readlink -f /opt/srdq/current
sudo systemctl status \
  srdq-pg.service \
  srdq-controller.service \
  srdq-web.service \
  'srdq-executor@*.service' \
  --no-pager
sudo -u srdq-ctl env SRDQ_CONFIG=/etc/srdq/config.yaml \
  /opt/srdq/current/venv/bin/srdq status \
  > "/tmp/srdq-status-before-${VERSION}.json"
sudo /opt/srdq/bin/srdq-pg-backup --label "manual-before-${VERSION}"
df -h /opt/srdq /var/lib/srdq /tmp
```

同时人工确认：

- 当前没有运行中的校验计划。
- 没有人在 Web 上执行导入、确认或运维操作。
- 六个 StarRocks FE 地址从生产机可达。
- 数据库备份已额外复制到 ECS 外受控存储。
- 第 0 章所有上线门禁均已关闭。

### 步骤 10：解压并检查包内校验

```bash
cd /tmp
tar xzf "srdq-offline-${VERSION}-alinux4-x86_64.tar.gz"
cd "srdq-offline-${VERSION}"
sha256sum -c SHA256SUMS
```

包内校验有任何失败时停止升级。

## 5. 执行升级

### 步骤 11：运行升级脚本

```bash
cd "/tmp/srdq-offline-${VERSION}"
sudo ./deploy/upgrade.sh
```

脚本应依次完成：

1. 校验 root 权限、主机架构、glibc、Python 3.11、systemd 和包内 checksum。
2. 安装新 release 和 PostgreSQL 二进制。
3. 记录当前服务，保存旧配置快照并停止应用服务。
4. 创建 `pre-<新版本>` 数据库备份。
5. 安装 systemd 单元和生产配置，保留已有 worker token。
6. 执行数据库增量迁移和多集群拓扑初始化。
7. 为六个 Executor 签发或保留 token。
8. 原子切换 `/opt/srdq/current` 并恢复服务。
9. 输出升级前备份和完整回退命令。

成功输出类似：

```text
upgraded srdq <旧版本> -> <新版本>
backup: /var/lib/srdq/backups/<时间>-pre-<新版本>.dump
rollback: /opt/srdq/deploy/rollback.sh <旧版本> /var/lib/srdq/backups/<时间>-pre-<新版本>.dump
```

立即把这三行保存到变更记录。不要关闭终端或删除备份。

## 6. 升级后技术验收

### 步骤 12：确认版本和配置

```bash
readlink -f /opt/srdq/current
sudo env SRDQ_CONFIG=/etc/srdq/config.yaml \
  /opt/srdq/current/venv/bin/srdq check-config
sudo -u srdq-ctl env SRDQ_CONFIG=/etc/srdq/config.yaml \
  /opt/srdq/current/venv/bin/srdq status
```

确认当前链接指向新版本，配置版本为 `srdq-config-v1.4`，并显示三个校验组。

### 步骤 13：确认服务

```bash
sudo systemctl is-active \
  srdq-pg.service \
  srdq-controller.service \
  srdq-web.service \
  srdq-executor@huawei-1.service \
  srdq-executor@aliyun-1.service \
  srdq-executor@huawei-2.service \
  srdq-executor@aliyun-2.service \
  srdq-executor@huawei-3.service \
  srdq-executor@aliyun-3.service
```

所有输出都必须为 `active`。再确认旧实例已经停止且未启用：

```bash
sudo systemctl is-active \
  srdq-executor@huawei.service \
  srdq-executor@aliyun.service
```

旧实例应输出 `inactive` 或 `unknown`，不能仍为 `active`。

查看本次启动日志：

```bash
sudo journalctl --since '-15 min' \
  -u srdq-controller.service \
  -u srdq-web.service \
  -u 'srdq-executor@*.service' \
  --no-pager
```

不得出现迁移失败、凭证权限错误、token 拒绝或重复重启。

### 步骤 14：确认接口和页面

```bash
curl -fsS http://127.0.0.1:8470/v1/health | python3.11 -m json.tool
```

随后登录 Web，逐项检查：

1. 看板显示六个物理集群以及 COUNT、METRIC、SAMPLE、METADATA、DEEP 五类池。
2. “执行器”页显示六个 Executor 在线且 `cluster_id` 正确。
3. “范围清单”中的每个资产只属于一个 `pair_id`。
4. “计划”可选择单个、多个或全部校验组。
5. 历史资产数量、规则数量、计划数量与升级前记录一致。

## 7. 业务冒烟验证

### 步骤 15：执行最小验证

在正式窗口前，用经过审批的小范围测试资产执行：

1. 每个 `pair_id` 至少选择一个资产。
2. 创建包含 COUNT、METRIC、SAMPLE 的测试计划。
3. 启动运行，确认三类检查可以并行领取。
4. 确认每项工作只进入所属 pair 的 SOURCE/TARGET 集群，不能出现跨组比较。
5. 查看报告和看板中的 cluster × pool 吞吐、P95、超时率及 ETA。

冒烟失败时不要开启正式计划，按第 8 章处理。

## 8. 失败处理和回退

### 8.1 迁移前失败

升级脚本应自动恢复旧 release、旧配置和原服务。执行：

```bash
readlink -f /opt/srdq/current
sudo systemctl status \
  srdq-pg.service \
  srdq-controller.service \
  srdq-web.service \
  'srdq-executor@*.service' \
  --no-pager
```

确认业务恢复后，根据错误修复离线包；不要在生产机直接修改 release 或包内文件。

### 8.2 迁移后失败

迁移后不能只切换软链接。必须使用升级脚本打印的旧版本号和升级前 dump：

```bash
sudo /opt/srdq/deploy/rollback.sh \
  <旧版本> \
  /var/lib/srdq/backups/<升级前备份>.dump
```

回退会：

1. 再创建一份当前数据库安全备份。
2. 删除并从升级前 dump 重建控制库。
3. 恢复旧 release 和旧配置快照。
4. 进入 RECOVERY 模式并重启服务。

升级后产生的结果、导入和确认操作都会丢失。回退完成后，确认旧执行器和数据库一致，再执行：

```bash
sudo -u srdq-ctl env SRDQ_CONFIG=/etc/srdq/config.yaml \
  /opt/srdq/current/venv/bin/srdq recovery confirm \
  --reason '<审批单号和恢复确认说明>'
```

未完成核查前不得确认 RECOVERY。

## 9. 收尾

升级和冒烟均通过后：

1. 保存版本号、checksum、升级输出、备份路径、日志和验收截图。
2. 保留升级前 dump，直至至少完成一个正式夜间窗口并验收报告。
3. 按敏感制品制度删除 `/tmp` 中的压缩包和解压目录。
4. 不要删除 `/opt/srdq/releases/<旧版本>`，直至回退观察期结束。
5. 次日复核六个集群五类池的完成量、P95、超时率和 ETA。
